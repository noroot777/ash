# 验收前置命令的源码与运行凭据

项目的 `acceptGateCommand` 在点验收时执行。目标分支不存在、被其它 worktree 占用、目标工作区不干净或依赖尚未就绪等廉价检查先运行；测试通过后真正合并前仍重新检查。

## 被测源码

Git 项目先要求任务工作区的索引和工作树干净，包括未跟踪文件。测试不再在该工作区直接执行，而是在独立 clone 的 detached 提交上执行。该 clone 不共享可写工作树、索引、refs 或 Git 对象硬链接，也不保留指向原工作区的 remote。

快照提供已提交文件，以及根目录、已提交包清单（`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`composer.json`、`Gemfile`）所在目录中现有的 `node_modules`、`.venv`、`vendor`、`target`。

依赖**不**逐文件深拷，放法有两种，判据是**依赖树里有没有一条链落回项目自己的源码**：整棵树走一遍（遇链不跟随，所以不绕圈），有一条就必须隔离。不取项目的 workspace 声明——`workspaces` 只是本地包进 `node_modules` 的若干写法之一，`"aliased": "file:./packages/lib"`、`npm link`、lerna bootstrap、pnpm 的 `link:` 都建出同样的链，而**目录项名可以和包名毫无关系**（`node_modules/aliased` → `packages/lib`，那里的包叫 `@demo/lib`）；声明的漏法永远落后于包管理器的新写法，扫描的漏法靠「走遍每一个条目」能消掉。走一遍的代价本仓实测 166 毫秒 / 47501 个条目 / 37 条链（对照全量字节摘要一遍 6.9 秒）。判据的第一道其实是**安装记录认下的自有包**（归属以依赖树自己所属的那个检出为准）：落点扫描只认「落回本检出源码」的链，借来另一个检出那棵树时它一条都扫不出来，而那恰恰是最该隔离的形状。认不下再扫落点兜底。判据不能换成「树在本检出之外就克隆」——纯粹的共享安装目录（里面全是第三方包）借用是安全的，克隆只是白拷一整棵树。声明过 workspace 的项目**叠加**往隔离那侧倒：那是一道不花钱的保守闸。**没有这种链、也没有声明**：快照里这些目录是指向工作区那一份的链（POSIX 目录软链 / Windows junction），建它是 O(1)。此时**测试写进依赖目录的东西会落到工作区**——vite 的 `node_modules/.vite`、各类 `.cache`、Rust 的 `target` 增量产物都会；这与自己跑一次测试产生的是同一类内容，但它不在快照的隔离范围内。只读做不到：改权限等于动工作区，而 `.bin` 仍需可执行。**有其中任何一样**：`node_modules` 整棵克隆进快照（数据块共享，macOS clonefile / Linux reflink；本仓实测 9.8 秒、实际占用 16 MB，对照不共享是 5.0 秒 / 684 MB；Windows 没有对应物，那里退回普通复制）。克隆形态没有写入外溢，快照有自己的一棵树。建链失败（跨卷、权限、Windows 上 junction 与目录链都不成）也走克隆，不再留一条「逐文件深拷」的退路：那条退路拿不到数据块共享，也不过对账。两种形态下依赖的身份都取**安装声明**（`node_modules/.package-lock.json`、`.modules.yaml`、`.yarn-state.yml`、`vendor/modules.txt`、`composer/installed.json`，虚拟环境取 site-packages 下的 `*.dist-info`），不逐字节重读整棵依赖树：装、删、升级任何一个包都会被认成「依赖变了」，而**手改依赖目录里的文件却没重装**（patch-package 打完未提交、`npm link` 指到本地检出、进去改一行热修）不会——那种改动会沿用上一张通过结果。换这个口径省掉的是每次至少三遍全量摘要（本仓一遍 6.9 秒、整棵 563 MB / 45490 文件），代价就是这一处检测力。身份还有**向上继承**的那一半：node 按每个包名分别一级级往上找，所以任务自己那棵树（已登记在 `dependencies` 里）之外，祖先每一棵都是这次测试的实际输入——工作区没装依赖时它们就是全部输入，而它们从来不在那份清单里。这部分摘要单独成一项（`source_ambient`，口径见 `accept-gate-deps.ts` 的 `ambientDigest`），只进「这张绿还算不算数」的复用判据，**不混进 fingerprint**：那一项还要被「副本是否按原样复现」的对账拿快照自己重算一遍，而快照住在运行产物目录下、向上继承的是另一条链，混进去会让每一次快照都判成没复现。漏掉它的代价是实测的：祖先树里的包正常 `npm install` 升一个大版本之后，重新建的快照执行输出已经是新版，而源码指纹一个字节没变，于是上一张绿被判成「同一份输入」继续沿用。换口径让存量绿结果一律失效、各重跑一次，这是预期的。

monorepo 必须克隆而不能借用，因为 node 的模块解析走 realpath：借用之后依赖树的解析根仍在快照外，于是三条路都落在**活的工作区**上——直接 `import` 那个 workspace 包、被借包内部的传递导入（`node_modules/plain` 里 `from "@demo/lib"`）、以及 `.bin` 下的 CLI shim（workspace 包声明 `bin` 是最普通的形状）。依赖根整条指向**另一个检出**时更直接：快照会跑那个检出的源码，而本任务的源码明明已经 checkout 在快照里，这一条不需要任何并发修改就会把错的代码判成通过。判据是「扫一遍依赖目录，看有没有链落回源码」而不是项目自己的声明。扫描曾被否掉的理由是「漏一层就把没隔离的副本判成合格」，而那是**限定层数**才有的漏法：遍历不设深度上限、判据取原生落点而不是链的形状，上面后两条（传递导入、`.bin` 下的 shim）就都在扫得到的地方——它们本身就是那棵树里的条目。Python 的 editable install 把源码路径写进 `.pth`/`.egg-link` 的文件内容而不是链，克隆照抄内容等于照抄那条绝对路径，这类解冻目前不处理（深拷也一样，不是放法引入的）。glob 按段匹配，`*`/`**` 可出现在任何位置（`**` 深度上限 8 层），但它**不承担隔离**：npm 接受的声明写法比任何展开器都多（`packages/{lib,other}` 这种 brace 实测 npm 认、展开器当成字面目录名），而「展开不出来」曾经直接等于「这个项目没有 workspace 包」。隔离改由两件与声明语法无关的事保证。一是**归属取安装记录**：`.package-lock.json` 里每条 link 条目的 `resolved` 指向项目内就是自有包、指向项目外就不是（npm 把 workspace 包和 `file:` 依赖都装成链，两者的路径后缀和 `package.json.name` 可以完全一样——两个同名包是合法的，名字和路径都不是来源），读不到记录就一条都不改写，隔离失效会被对账当场抓住。二是**运行入口收口**，口径只有一句：**证明不了，就无副作用地拒绝**。快照建好之后，枚举 node 实际会用到的每一个运行入口 —— 从快照一级级往上的每棵依赖树，包入口、`@scope/包`、别名目录项、`.bin/<命令>`、以及嵌套在包里的那一层 `node_modules`，按入口路径去重（近的树遮住远的，和运行时一致）；可达性由 `stat` 给出、落点由 `realpath` 给出（只用 realpath 会把一条原生读不通的链——原文带尾部分隔符却指向普通文件——当成活源码入口，于是合法项目在门禁开跑前被拒）。落点落在快照里、或落在它自己那棵树里（普通第三方包）就不管；剩下的按三条不变量处理，**全部校验走完才动手写**，所以拒绝的那条路上快照之外一个字节都没动。**① 写入所有权**：每个计划目的地的**完整父链**逐段 `lstat`+`realpath`，每一段都得真实落在快照内（还不存在的那一段往下都是新建，安全；落在快照外、或解析不通都拒绝）。只验 `node_modules` 这个根是不够的：`node_modules/@demo` 可以是一条指向另一处安装存储的链，根是真目录所以检查通过，而`rm(<快照>/node_modules/@demo/lib)` 穿过它会把用户原安装存储里那个包目录整个删掉（macOS 上写后核对才报错、破坏已不可逆；Windows 的 junction 用绝对落点，连错都不报）。字面路径在快照内、根在快照内，都证明不了实际写入目的地在快照内；也不能给 `@scope` 加白名单——路径里任何一段都可能是链。**② 来源身份**：「这个入口是本项目自己的包」只认**安装记录**（`.package-lock.json` 的 `link` + `resolved`），建立「安装入口 ↔ 安装来源 ↔ 本次提交目录」的三元映射。入口路径相等是最强的一手（记录说它装自项目内某个目录，落点此刻指到哪都不改变这个事实）；落点落在某个自有包**内部**时（`.bin/demo-cli -> ../@demo/lib/cli.mjs` 就是这形状）把包内那段相对路径一起带过去，否则 CLI 入口会指着一个目录。记录指向的目录在本次提交里不存在时，才按**包名**在快照源码里兜底找一次，且要求**唯一命中**、而且候选必须**由本次提交的声明指向**（`workspaces` glob 或 `file:`/`link:` 依赖规格）——包搬过位置（`packages/lib` → `libs/lib`）是合法重构，不该让验收不可用，而此刻「它是自有包」已经由记录证明过，名字只用来回答「搬到哪了」；但光有「唯一同名」证明不了搬迁：原目录被**删掉**、仓库里另留一份同名副本（`examples/lib`、`patches/lib`）的布局会让安装入口绑到那份无关副本上，等于把被测代码换成另一份还报绿。真正的搬迁一定同步改过声明（不改 npm 装不出来），所以声明是那条「可核实的迁移对应关系」，证明不了就拒绝。绝不反过来按源码里的 `package.json.name` 认来源：项目正式依赖一个第三方包、仓库里另存一份同名的 `patches/<包>`，按名字认会在快照里建一条更近的绑定，**遮蔽项目实际使用的正式包**（实测工作区 `REGISTRY_1_3_0`、快照 `PATCH_COPY`，而自证为真——换掉被测代码还报绿）。来源分**三态**，不是两态：记录认下装自项目内的是自有包；记录认下装自项目**外**的（`file:../另一个仓库`）是**已知外部来源**，照既定外链策略原样留着；两者都没认下的才是来源不明。把已知外部那一态并进「不明」的代价是实测的（两平台一致）：一个正常 `npm install` 装好的外部 `file:` 包住在独立 Git 仓库里，于是被当成未隔离的活源码拒掉，门禁说「安装记录里没有这个入口、请重新安装依赖」，而重装只会得到同一份合法记录——项目永久过不去；外部包由不由 Git 管理不改变它是明确外部来源这个事实。来源不明时再分两种：记录读到了却没认下、而落点又是某个 Git 检出的活工作区源码的，是「装出来的东西和记录不一致」，拒绝；落点压根不在任何检出里的（系统工具 `/opt/homebrew/…`、手铺的 vendor 目录）本来就不是这次要冻的源码，不需要隔离，也不因「来源无从证明」被拦（否则一个手铺依赖树带一条系统工具链的项目永久过不去）。**③ 入口闭包**：根 `import` 修好不等于隔离成立——实测根 `import` 已是 `TASK_NEW`，同一份快照里 `.bin` 的 CLI 跑出来是 `MAIN_OLD`，改主检出后它跟着变成 `MAIN_LIVE`，而自证全程为真。元数据缺失只说明**来源尚未证明**，不是跳过证明的理由：没有安装记录就拒绝，绝不静默保留一个指向活动主检出的入口。闭包还有**消费者**那一半：往 `<快照>/node_modules/<入口>` 补一条绑定只对「从快照根出发」的解析有效，而快照之外那棵树里的第三方包是从**它自己的位置**向上解析的，先命中那棵树里的原入口。实测形状（真实 npm 离线安装）：主检出有 workspace 包 `@demo/lib`，另装了第三方包 `plain-consumer` 传递导入它，任务 worktree 没装依赖——同一份快照里直接 `import` 得到 `TASK_NEW`、经 `plain-consumer` 间接 `import` 得到 `MAIN_OLD`，改主检出源码后它变成 `MAIN_LIVE`，而自证全程为真。判据仍是可证事实：那棵树上除了自有包入口**还有没有别的入口**。没有（整棵树只摆着本项目自己的包）时根上的绑定就是全部解析路径；有别的入口时它们都是潜在消费者，「它会不会 import 本项目的包」要静态分析整个包才知道，证明不了就拒绝，并告诉用户出路（在任务工作区装依赖，或让依赖目录成为工作区自己的一条链，门禁会把它整棵克隆进快照——克隆形态不受这条约束，消费者的副本也在快照里）。**两处覆盖不到**，写在这里以免被当成已包住：Windows 上 npm 生成的 `.bin/*.cmd`/`*.ps1` 是真文件、相对路径写在内容里（和 Python 的 editable install 同类，要改得重写文件内容，这一层只处理链形态；开发者模式下 npm 建文件软链，那种形态覆盖得到）；快照**外**那棵树的嵌套层（`node_modules/a/node_modules/@demo/lib`）没法从快照遮蔽（node 从 `a/` 内部解析时先看它自己那层），所以那种布局只能拒绝。这条收口不能省：工作区没装依赖时（worktree 的常态）快照里压根没有依赖树，前面每一条检查都「通过」，而 node 按**每个包名分别**一级级往上找，就找到项目主检出那一份，顺着 workspace 链读到**活的**工作区源码——实测快照自带 TASK_NEW、执行输出 MAIN_OLD，随后把工作区改成 MAIN_LIVE，同一份快照的输出也跟着变，而自证全程为真。

依赖树里的软链一律按原样重建，不跟随、不拍平成真文件。克隆时每条链按**原生落点**分四类决定新指向：依赖树内部的相对原文照抄；树内的绝对原文、项目源码、以及**安装记录**认下的自有包都改写到快照内对应位置（Windows 的 npm 给 workspace 包建的就是绝对 junction，而依赖树借自另一个检出时那条链指的是**那个检出**的源码，所以要把它接回快照自己那份；判据只能是安装器写下的 `resolved`，不是路径后缀也不是包名——一个恰好装在同名目录下、恰好同名的第三方依赖被换成项目自己的包，等于换掉了被测代码还报绿）；落在快照外的一律改写成绝对路径指向原落点（相对外链照抄到不同深度就会指空，那是本地跑得通、门禁里 ENOENT 的来源）；父目录都解析不到的照抄，保持原样不可达。可达性与落点一律由**原生调用**给出（`stat` 判可达、原生 `realpath` 解析父路径、末段不解析），这个模块不自己解释任何一个路径字符：`…/file/` 原生读是 ENOTDIR（抹掉尾部分隔符会让本地失败的用例在门禁里成功）、POSIX 上以字面 `\` 结尾的文件名不是「带分隔符的目录」、穿链之后的 `..` 必须按原生顺序解析（词法先消掉 `bridge/..` 指向的是另一个文件）——自己切分路径这三条都会错，而且对账那一侧必须用同一个判据：只用 `realpath` 判可达会把两侧都读不通的那条链判成「副本放错了」，门禁在一个合法项目上直接不可用。这套搬迁判据与对账共用一处，靠自身位置做相对解析的运行时（`.bin` 下的 cli、虚拟环境的解释器链）否则一启动就失败。环和断链不拒绝整棵树；依赖根**自己**不可达（没装的可选依赖、悬空链、环）时在快照里照原样重建成同样解析不通的那一条，而不是判成复制失败。ash 的运行产物目录（`ASH_RUNS_DIR`，可配）既不是测试输入也不跟进副本，源码复制与依赖克隆共用同一份排除计划；它落在依赖目录内部时，复制遍历还会按落点挡住**正在创建的快照自己**，否则会一层层把快照拷进快照直到路径过长。其它被 Git 忽略的文件（例如 `.env`、本地数据库和自定义依赖目录）不自动复制。需要这些内容的命令可能失败，可将可复现输入纳入版本管理，或明确决定本次跳过。借用虚拟环境不等于重写内部绝对路径，也不保证它可跨机器运行。Git 子模块及指向快照外的**源码**符号链接拒绝运行；依赖目录是上面那条规则的明确例外。

命令产生的未跟踪构建产物只留在快照里。Windows/Linux 在整次进程退出被证实后删除快照；macOS 兼容监督保留快照，避免把观察范围内的退出误当作所有后代退出而删除目录。命令修改已提交源码或改动快照的 HEAD 时，即使退出码为 0 也不放行；这一条对**依赖目录豁免**——借用形态下它在快照里本来就被换成一条链，`git diff HEAD` 看到的是一整棵「已删除」，不豁免的话把依赖目录一起提交的项目（Go 的 `vendor/` 是官方推荐做法）一次验收也过不去。豁免范围取**本次真实登记并放置的那几条路径**，落盘在快照的 sidecar 里，首次执行、收尾与重启恢复读同一份；读不到计划时一条都不豁免。按「路径里出现过依赖目录名」放行是不够的：一个压根没有依赖目录的项目里，命令改掉 `web/src/vendor/lib.js`、`docs/target/spec.md` 这类**按提交冻结的普通源码**也会被判成没变，验收照样放行。登记那一侧同样只认类型不认名字：提交一个叫 `vendor` 的普通文件不是依赖目录，它按源码冻结。非 Git 项目复制普通文件与目录，以内容指纹和起跑输入清单核对；原目录输入变化会使结果过期，测试修改原有输入不会为原目录放行，快照内新生成的构建产物不影响原输入身份。

这是执行前后的源码一致性校验，不是恶意命令沙箱或逐次写入审计：命令修改源码后恢复原字节且 HEAD 不变，结束时的检查无法发现这段历史。未提交/未跟踪源码的拒绝是可复用提交凭据的边界，不会自动提交、删除或忽略这些文件。

复用依据为命令、源码提交和输入指纹；自动续验收、手动复用、批量预判与状态新鲜度共用这一判据。旧的仅有提交号的结果不再复用。真正的 Git 合并读取被测提交号，而不是再次解析可变的任务分支；分支不再指向该提交时拒绝合并。目标分支前进后的非 fast-forward 合并仍只记录被测范围，不宣称测过最终合并结果。

只有通过记录可用于放行。失败、超时、取消或被打断后，重新点验收会产生一次新运行，即使源码没有变化；旧失败保留为历史，不再直接挡回同一次验收请求。已有运行或尚未证实退出的进程仍阻止重跑。卡片显示运行 ID、开始与结束时间，区分历史失败和新的执行。

本仓库的 `npm run test:accept` 及回归登记 worker 启动被测子进程时移除继承的 `ASH_DB`、`ASH_RUNS_DIR`（包括大小写变体），测试可自行创建临时数据目录。worker 本身仍连接原记录库，保存日志、退出码与证据；命令中显式指定的环境变量不受影响。

## 进程能力与恢复

门禁命令在启动器的监督归属登记完成后才获得执行许可。Windows/Linux 使用整次运行的内核退出证据；macOS 使用下述明确分档的兼容监督，不把它标成内核围栏或整次运行证明。

- Windows 使用门禁专属的独立 Job supervisor，在实际打开的进程句柄上核对创建时间，再用同一句柄加入 Job，持久化带代际的归属与集合为空的终结凭据。编译及等待登记使用异步路径，不再同步冻结服务事件循环。服务进程退出后仍可以恢复查询；Job 名字不存在但没有终结凭据时不放行。
- Linux 使用可写的 cgroup v2；无法建立或恢复集合时拒绝授权或保留停止责任。
- macOS 实际执行同一条验收命令，使用 `macos-observed` 兼容监督：原生读取进程组、父子关系、微秒级启动身份与 `KERN_PROCARGS2` 的 NUL 分隔环境项，精确匹配每次运行的继承标记；观察到的成员身份落盘并定期刷新。取消、超时、正常结束和服务重启后的恢复都先收尾这些进程，每次发信号前重新核验启动身份，不根据 `ps` 的环境展示文本杀进程。监督读取失败会保留占用，不按退出处理。

macOS 仍没有等价 cgroup/Job 的完整保证：在两次观察之间出生、清空标记并脱离进程组的后代可能无法识别，兼容模式不宣称覆盖它们。通过表示命令 rc=0、已识别进程收尾完成且源码核对通过；启动记录持久化 `observed-empty` 而非 `kernel-empty`，验收卡、日志及时间线均显示这一范围。测试快照不自动删除，路径保留在日志中；这会占用磁盘，也不代表不可识别的后代已退出。编译原生监督器需要本机 Xcode Command Line Tools（`/usr/bin/clang`）；编译失败按实际启动失败处理，不会跳过测试或改写项目命令。旧 macOS 记录缺少这一监督身份时仍保留原有停止保护，不会仅因升级就放行。

缺失新字段但已持久化 `armed` 和内核归属的旧记录，会在能重新查询真实集合时补录登记凭据；集合消失仍不冒充空集合。无法恢复的记录继续阻挡合并与清理，取消后可在两处门禁卡展开“确认风险并强制释放”。该动作需要指定运行 ID 和二次明确确认，持久化为 `interrupted/ownership_waived`，写入日志与时间线，清空可复用源码身份，保留独立快照，不向身份不明的 PID 发信号。它只是人工放弃停止保护，不是内核退出证明或测试通过；残留进程仍可能写文件，后续合并、删除与接力可能有风险。重复确认幂等，保存失败则保留占用。单个根进程退出仍不会自动核销责任。取消时若终态写入失败，响应为 `settlement_failed`，界面提示重试；运行占用与未结算状态继续保留，避免显示“已经结束”。

Git 快照建立时同时计算副本指纹，验收判定与复制后的原输入仍完整核对。借用之后两侧读的是同一份依赖文件，摘要恒等，所以依赖这一侧改按**落点**对账，三种形态各对一件事：整条借出去的要落在工作区那一份上，不可达的要在副本里同样不可达，克隆过的要落在快照内、每个落点指回源码的条目都解析到快照自己那份源码、**而且**整棵树的链闭包逐条落点等价（两侧各自解析一次再比，而不是看链的文本像不像——「原文照抄」恰恰是相对外链失效的原因，而「根在快照里」证不了树里每条链还指得对）。对账排在源码与依赖都落盘之后——克隆形态要解析快照里的 workspace 包，那条路径由源码提供。状态新鲜度查询不再逐字节重读依赖树，但仍是真正的验收判据而非陈旧缓存。批量预判在本机能力或源码输入不可用时不会谎报“即将起跑”。

macOS 的独立原生 guardian 在授权前加入启动器的进程组与会话，微秒级身份随监督记录持久化；它在命令父进程退出后继续锚定这一组的代际。因此清空环境但没有脱组的后代仍会被纳入收尾，不依赖恰好赶上一次采样。组成员由原生进程组查询补核，成员不可读或组代际无法确认时保留占用，不向可能复用的组盲发信号。整组及已识别成员收尾后关闭这一代际，再结束 guardian；显式强制释放在保存成功后销毁扫描器和自己的 guardian，不把放弃责任写成退出证明。较旧的观察记录缺少 guardian 凭据时不自动升级为新证明。

## 跨机接力

导出与移回携带冻结的验收方式、凭据运行 ID 和已结束的门禁历史；日志通过普通运行产物搬运。PID、内核集合、启动控制文件、测试快照和自动续验收选项不跨机携带，仍有停止责任的运行阻止接力。附件预览与导出共用运行产物枚举器，在递归前排除保留快照与监督文件，不读取快照依赖里的文本或把其中的路径算成待迁移附件。

导入将运行记录和日志地址映射为本机路径；移回时事务性替换历史，重复同一次传输保持幂等。迁入记录只证明历史，不直接作为当前机器重跑或复用的凭据。日志超限未携带或已被清理时，界面明确显示“当前不可查”，日志接口也不把缺失冒充为空日志。

## 回归入口

- `npm -w server run test:accept-merge`：合并、门禁编排、源码身份与生产进程能力测试。
- `npm -w server run test:handoff-accepted-return`：已验收任务移回、门禁凭据与日志双向接力。
- `npm -w web run test:accept-gate-dom`：真实无头浏览器中的取消失败反馈和日志缺失提示。

POSIX 上的编排回归使用仅存在于测试启动器中的进程组夹具，不代表生产围栏可用；生产进程、detached 后代和跨控制进程恢复用例独立运行，不加载该夹具。
