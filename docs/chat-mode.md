# 聊天模式

聊天入口位于工作区侧栏，以及新建面板的「单任务 / 团队 / 讨论 / 聊天」第四项。
群聊是项目下独立的持久会话，不参与一次性任务的完成、验收或队列结算；从聊天委派出来的工作仍是标准 ash 单任务。

## 本轮实现

- 群聊可创建、切换和配置成员，所有已注册的智能体类型均可参与，不限 Claude。每位成员使用现有的「智能体 · 模型 · 智能水平」选择器，保存具体执行器配置；CLI 安装、登录与供应商配置沿用 ash 原有要求。
- 用户消息里的明确 `@成员名` 触发回复。无点名的消息只保存；智能体回复中的点名不触发其他成员。代码块、行内代码和 Markdown 引用里的点名不触发。
- 被点名的成员获得该群共享摘要和近期完整消息；未被点名时不运行、不接收新消息。一次可点名多位成员，同群同成员的回复串行，聊天与历史摘要合计最多四个并发 CLI 调用。
- 咨询返回简短答复；明确的执行委派由被点名的智能体返回结构化任务描述，服务器创建并启动 ash 单任务。聊天回复最多 300 字；任务详情和完整执行日志位于任务页。
- 任务卡通过 SSE 更新运行状态、验证阶段和待答问题。任务完成时卡片显示结果就绪，不额外唤醒群成员。复杂任务默认采用独立 worktree；非 Git 项目按已有逻辑使用原目录。
- 停止回复会同时停止当前群正在运行与排队的聊天回合，以及历史摘要整理，结果持久化。已经创建的任务不受「停止回复」影响，可以打开任务页管理。
- 消息编号防止重复发送导致重复唤醒；服务重启后未完成聊天回合显示中断，不自动重新执行。再次点名可发起新回合。
- 界面包含频道导航、点名补全、成员状态、简短消息和任务卡；消息入场、点名菜单、任务状态及按钮有动效，并尊重系统减少动态效果设置。390px 宽度下聊天独占主工作区。
- 从任务新建面板切到聊天再切回任务时保留正文和已上传附件，不把任务草稿自动发送到群里。

## 范围与取舍

第一版是「当前用户 + 多个智能体」的群聊。多人实例中，群聊同时受创建者归属和项目可见性限制，不是多人类账号共享频道。

消息保存在 `chat_rooms` / `chat_messages` 表。页面展示最近 500 条，历史仍保留在数据库；模型上下文使用持久共享摘要和近期完整消息，不再按 48,000 字符滑动截断。页面的 500 条展示上限不再限制摘要可读取的历史范围，也不读取其他群。

### 上下文预算与后台预压缩

普通轮次保持摘要不变，只追加完整消息。历史按稳定的 `role / author / body / taskId` 文本冻结到 `chat_context_entries`，运行状态和时间戳不占提示词空间，也不会反复改写前缀。发送时记录历史序号；排队期间完成的回复或之后发出的消息不会倒灌进该请求。

默认管理预算为约 24,000 输入 token。当前没有跨 CLI 通用 tokenizer，采用 ASCII 约 3 字符/token、非 ASCII 约 2 UTF-8 字节/token 的估算；这不是供应商实际窗口上限。前台检查扣除固定提示词、浏览器规范和本次用户消息，再决定是否先整理历史。CLI 自身的系统提示和工具开销不能从这个估算中精确获知，实际缓存命中和费用仍取决于模型、供应商与使用情况。

一轮回复结束且本群没有待回复成员时，历史超过约 16,000 估算 token 才启动后台预压缩，复用刚完成回复的成员配置与现有 CLI 登录方式。压缩后通常保留约 6,000 token 的近期完整消息，较早部分合并为最多约 2,000 token 的摘要，因此不会每轮整理。未点名的普通消息只入库，不单独启动摘要调用；积压历史过长或后台未赶上时，下次被点名的前台准备阶段按需补做。

摘要调用在临时目录运行，只整理提供的文本，工具事件会终止该调用。摘要保留目标、用户确认的决定与约束、关键引用、任务编号、未解决问题和分歧；校验通过后保存到 `chat_summaries`。旧摘要版本与原文保留，已经排队的请求仍能读取其快照对应的版本。长历史按完整消息分批整理，没有字符截断或静默丢弃；无法整理的超长单条消息会明确报错。

同群的整理串行去重，`@all` 共用结果；聊天和摘要共用四路调用额度。后台失败不会覆盖已完成的聊天回复，整理状态经 HTTP/SSE 返回并在输入区持续展示。失败后前台一分钟、后台五分钟内不重复尝试摘要；随后由新点名/回复结束按需重试，没有定时空转。停止会取消整理并保留已保存的摘要与原文；服务重启把在途整理标为中断，不自动重启模型，下次点名时按需继续。

相关回归：`npm -w server run test:chat-context` 覆盖触发阈值、前缀稳定、旧群完整历史、多人去重、发送快照、后台取消、失败冷却和重启复用；`test:chat-execution` 覆盖摘要调用的临时目录、禁用工具及清理；聊天浏览器回归覆盖整理中、停止/失败的刷新持久化、摘要完成和窄屏提示。

### 重新开始上下文

在群里单独发送 `/clear`（大小写不敏感）会停止本群在途和排队回复、取消后台整理，并建立新的上下文起点。命令本身不调用模型。旧消息和任务卡仍可查看，旧摘要版本仍保存在数据库，但后续成员回复与新的摘要不会再携带这个起点之前的内容；其他群不受影响，已创建的任务继续按任务页管理。

清空命令、可见分界提示和新的历史序号在同一事务中保存，重复发送同一消息编号不会重复清空。输入区也显示持久提示，刷新和服务重启不会恢复旧上下文。引用、代码里的 `/clear` 或带其他文字的消息不被当作清空命令。

本轮验证：聊天全量回归（含上下文和清空）、多用户回归、server/shared 构建、web 类型检查、规范检查及 Vite 生产构建通过。`ASH_CHAT_SMOKE=1 npx tsx server/scripts/test-chat-cli.ts codex --summary` 通过真实 Codex CLI 的摘要格式、随机验收编号、已有决定保留和无工具调用检查；其他执行器的通道校验使用模拟工厂，不等同于全部真实模型实测。生产构建仍有原有的大 chunk 提示。

浏览器先尝试扩展具名后台会话「🔎 群聊摘要与清空」，返回 `Capability is not available: visibility`，无法保证后台标签，随后使用临时 profile 的独立无头 Chrome。未激活、接管或直连用户普通标签，未启动有头浏览器。首次新增断言因精确文本选择器包含停止按钮文字而超时；改为读取 `role=status` 后通过。最终聊天浏览器回归通过，并等待清空后的新回复完成，验证后台整理、停止/失败/清空的刷新持久化、旧消息可见、新对话不恢复旧摘要及 390px 布局。

咨询还是执行委派由被点名的智能体解释，不使用关键词规则替代语义判断。聊天通过原有 `resolveExecutorFor` 和 `executor.run` 调用选定 CLI，保留模型、智能水平、profile 参数及供应商/登录方式，不换成另一个模型 API，也不再提供 Claude 专属聊天通道。

被点名后，工作目录为当前群所属项目，允许读取文件、查询资料辅助回答；没有配置项目目录时才使用临时目录，结束时只清理临时目录，不删除项目。实际启动前重新校验项目访问权与执行器归属，不携带任务回合凭证，不恢复其他聊天的会话。已识别的只读工具事件不会令正常回复失败；群里展示最终简短答复，或持久的边界警告，不展示查询过程。

聊天提示明确区分读取/查询和执行修改：咨询不修改文件、安装依赖或提交代码；明确的执行请求返回结构化 task，由服务器创建真实任务。第三轮修复增加系统检测与失败结算，不再仅依赖提示词；它不是 OS 只读沙箱，不能保证 CLI 在首次报告之前没有产生副作用。

当前实现没有附件消息、消息编辑、线程回复、全文历史检索或群聊归档。消息正文按纯文本显示，任务卡跳转到现有任务详情。

## 用户澄清与第二轮审查修复

第二轮审查指出 Claude-only 不符合「所有智能体」的原需求。随后向用户确认具体场景：「你问 @Codex 登录页怎么改比较好时，允许它先查看项目文件，再给简短建议吗？真正修改代码仍等明确交代，再创建任务执行。」用户答复：「当然允许啊，要不然智能体咋干活啊」。

因此本轮恢复所有智能体与原 CLI 的工具能力，取消此前误加的「聊天回合禁用一切工具」前提；没有把这一答复解释为咨询可以擅自修改代码。中文点名、权限隔离、任务卡、停止持久化及临时截图输出的修复继续保留。

## 第三轮修复：检测与持久警告

- 工具流只放行明确的读取/搜索工具，以及保守识别的单条读取命令；写入工具、未知工具、安装/提交/脚本、带重定向或复合语法的命令会终止回复。工具参数不原样写进群聊警告，以免泄露凭证。
- 起跑前建立项目目录元数据基线并启动递归监测，收尾时在进程清理后再次比对。即使 CLI 没发工具事件，在监测范围内新建文件、修改已有文件、删除或重命名也不能伴随 `task:null` 被当作正常成功。监测到变动时会结束剩余调用，不等模型宣称完成。
- 边界错误以 failed 状态及具体相对路径/工具名写进群聊消息；刷新、服务恢复或恰好点击停止都不会清掉这条警告。不把未经授权的副作用自动包装成任务，也不自动回滚用户文件；用户可检查变更，再决定是否明确委派后续任务。
- 该方案是检测后中止与诚实报告，不是事前沙箱。CLI 可能执行完才发事件，不能宣称已阻止首次写入。并发编辑也可能触发警告，文案不把变更来源擅自归因于智能体。扫描不跟随目录内符号链接，不保证发现项目目录外且未上报的操作；ash 自身的数据目录（DATA_DIR、数据库所在目录、RUNS_DIR、UPLOADS_DIR）与项目根下的 `.git` 排除在监测外，以免 ash 自己的持久化和并发 Git 操作误触发。监测无法启动、核对失败或监测范围内超过 20 万条目时不会按正常咨询放行。

- 第四轮把“不深扫”等同于“不监测”的取舍已撤销；现在大目录内的变更也会保留明确告警，不再作为正常咨询放行。
- `npm -w server run test:chat` 的大工作区回归已在第五轮纠正：只读成功、不深度枚举；依赖与其他工作树内的副作用失败，源码及相似目录名仍告警，当前工作树根目录仍受保护。

## 第五轮修复：大目录不深扫但仍告警

- `node_modules`、`.worktrees`、`.claude/worktrees` 只保留目录根的 mode/mtime/ctime/inode 基线，不枚举后代；其后代的原生文件事件不再被忽略。第五轮的运行期排除项为 ash 数据库及附属文件、RUNS_DIR；第六轮仅补充下面列出的 linked worktree 索引缓存例外。
- 对没有深度基线的路径，事件到达后核对 ctime；已删除路径核对最近仍存在的父目录，从而覆盖新建后立即删除的情况。已在本次调用前发生的延迟事件不被当成新写入；目录根的收尾元数据比对作为补充。进程清理后保留 100 ms 收尾观察，再核对基线并处理完已收到的事件，避免同步返回直接关闭监测。
- 项目或依赖的并发变更同样可能触发 failed 警告，不能擅自归因于智能体。此方案仍是检测后中止，不是 OS 沙箱；未深扫的后代依赖系统文件事件，不能冒充完整内容快照，原有符号链接/项目外的监测限制不变。
- 回归覆盖四类大目录中的深层新建、等长修改、删除、重命名、创建后立即删除，假执行器同步操作后立即返回 `task:null`，不发工具事件、不人为延迟事件流；这些调用均失败。只读操作仍通过，测试还断言大目录从未被深度枚举。
- HTTP 与浏览器回归均补上 `node_modules/pkg/side-effect.txt` 复现：群中显示持久失败警告，刷新/服务恢复后保留，不创建任务、不自动撤销改动。浏览器截图为临时目录中的 `chat-boundary.png`，不覆盖已跟踪示例图。
- 真实主仓再次通过只读复现，`runCalled:true`、`task:null`，约 410 ms。测试数据库连接仍为临时库，未修改主仓或主数据库。后续重复验证观察到 `web/tsconfig.tsbuildinfo` 在调用期间变动，系统按预期告警；未为通过复现而增加忽略项。
- `test:chat`、大目录回归连续三次重跑、`test:multi-user`、服务端构建、前端类型检查、全工作区构建及聊天浏览器回归通过；最终收尾调整后再次通过聊天回归、服务端构建与浏览器回归。另用真实 Codex CLI 读取临时项目随机标记，结果准确、`task:null`、文件不变；不冒充全部 15 种真实 CLI 已逐一实测。
- 本轮在任何浏览器测试及包含浏览器步骤的构建之前，尝试扩展具名后台会话「🔎 依赖变更告警回归」；返回 `Capability is not available: visibility`，无法保证后台标签。因此使用临时 profile 的独立无头 Chrome，未启动有头浏览器，也未激活、接管或直连用户普通标签。

## 第六轮修复：其他工作树的索引刷新

- 仅将当前项目根下 `.git/worktrees/<name>/index` 与 `index.lock` 从基线、收尾比对和事件检查中排除，避免其他 linked worktree 的只读 `git status` 刷新缓存时中止主仓咨询。不忽略整个 `.git` 或整个 worktree 元数据目录。
- 当前工作区的 `.git/index`、主仓与 linked worktree 的 HEAD、源码、依赖及普通目录里的同名文件仍受监测；写入工具检查未放宽。例外依据精确路径，不声称能区分每次其他工作树索引写入的来源，也不将它描述为禁止任何 Git 元数据写入的沙箱。
- 新增 `server/scripts/test-chat-git-metadata.ts` 并接入 `test:chat`：真实临时 Git 主仓及 linked worktree，假聊天执行器只等待/回复，后台执行 12 次真实 `git status --short`；通过索引 ctime 和二进制内容变化确认缓存确实更新。修复前复现 `.git/worktrees/linked/index` 拒绝，修复后咨询成功，连续三次重跑通过。
- 同一测试验证 `index.lock` 创建/移除不会误杀，写入工具不能借缓存例外通过，当前索引、HEAD、源码、依赖及普通 `index.lock` 写入仍失败。临时数据库及 Git 仓库全部清理，不改用户仓库的源文件。
- 聊天全量回归、服务端构建、前端类型检查、多用户回归、全工作区构建与聊天页面回归通过；首次聊天全量回归曾出现一次原有 `.claude/worktrees: rename` 的预期拒绝未发生，未改该检测逻辑或放宽断言，原样重跑通过，保留这次间歇性观测。构建仍有原有大 chunk 提示。

## 第七轮修复：ash 自身写入与 Git 记账

- 前六轮的排除项是**逐个文件**加的：先是 ash 数据库三兄弟，再是 RUNS_DIR，第六轮是其他工作树的索引。群聊项目就是 ash 仓库本身时，这条路追不上——线上先后复现 `data/skill-calibrations.json` 与 `.git/index.lock` 两次误杀，被 @ 的成员齐刷刷回同一条中止警告。本轮改成按目录整棵排除。
- ash 自身数据目录：`DATA_DIR`、数据库所在目录、`RUNS_DIR`、`UPLOADS_DIR`（后三者可由 `ASH_DB` / `ASH_RUNS_DIR` / `ASH_UPLOADS_DIR` 改到别处，逐个解析）。`server.log` 每个请求都写，另有库锁、技能校准、`scratch/`、`tmp/`、`task-artifacts/`。某棵排除树反过来把项目整个罩住时忽略该项，以免看守形同关闭。
- 项目根下的 `.git` 整棵排除，取代第六轮「只豁免其他工作树 index」的窄例外：索引、锁、HEAD、`refs/`、`logs/`、`objects/` 都是 Git 的记账而非项目文件，且持续被 ash 的状态轮询、其他任务在同一仓库的提交、用户自己的终端改动。放宽不开口子——只读白名单里没有 `git`，智能体的任何 Git 调用在工具层即中止；真正改动内容的 `checkout`/`reset`/`stash` 必然同时改工作区文件，仍照常告警。工作区里的 `.gitignore`、同名 `index.lock` 等普通文件不随之豁免。
