# ash 接入飞书：形态与方案

状态：P1–P4 已实现（2026-11-06，任务 6aje7YwI4keW）。实现与方案的出入、实测结论见第十一节；前十节是方案稿原文，只改了与实现矛盾的地方。方案经过三轮：6 路调研（ash 代码 3 路，飞书平台、开源先例、个人知识库各 1 路），3 个视角各自出方案（MVP、架构、安全），再由 1 个审稿人对照代码和飞书官方文档挑错。下面写的是挑错之后的版本，关键代码断言都在本仓库里复核过。

## 一、结论

**推荐形态：ash server 进程内置一个 IM 通道模块，飞书是它的第一个适配器。** 在飞书侧建一个「企业自建应用 + 应用机器人」，由 ash 主动连出去走**长连接（WebSocket）**。一个 ash 实例对应一个飞书应用。

定位是**遥控器加决策收件箱，不是第二个主界面**。需要你拍板的节点（提问、待验收、失败）推成卡片，你在卡片上点一下就处理完；任务完成也推。长会话、diff 审阅、预览仍然回 web 看。

为什么这样选：

- **不需要公网 IP。** 长连接只要求机器能访问外网。新版卡片按钮回调 `card.action.trigger` 也能走长连接（只有旧版「消息卡片回传交互」不行）。ash 通常跑在家里的 Mac 上，这正好合适。
- **状态只存一份。** 提问、待验收、门禁结果都已经在 ash 的库里。外挂一个桥接进程，就得在那边再存一份，正好踩中先例里最常见的坑：待审批卡片只存在内存，重启就点不动了。
- **身份不用落明文 key。** 多人模式下库里只存 key 的哈希。外挂进程要代表每个飞书用户，就得替每个人明文保存 ash key。
- **能拿到全部事件。** `bus.ts` 是进程内的 EventEmitter，SSE 不支持断线续传，很多事件只是一个信号、要回查才知道内容。这几件事都只有在进程内才好办。

## 二、各种形态对比

| 形态 | 裁决 | 理由 |
|---|---|---|
| **server 内置通道 + 自建应用长连接** | **采用** | 见上 |
| 独立桥接 sidecar（cc-connect 一类） | 不选，只适合半天原型 | 状态要复制一份。SSE 断线就丢，信号类事件还要再发 HTTP 补内容。多人模式下要明文保存每个人的 key。自用模式下 :4317 监听所有网卡、零鉴权（`server/src/index.ts:625`），sidecar 一旦被做成对外暴露回调就是事故。先例里这类工具本来就是为「包一层 CLI」设计的，而 ash 自己就是调度器 |
| 群自定义 webhook 机器人 | 不选（最多当零配置的降级通知） | 只能单向推到一个群，收不到消息，按钮也回调不到服务端。webhook URL 本身就是凭据。ash 最有价值的恰恰是答复、验收这些回程动作 |
| 只给 agent 装飞书 MCP / lark-cli | 是另一件事，可以以后另做 | 那是「agent 去读写飞书文档」，不是「人通过飞书指挥 ash」。要做的话必须用**另一个**飞书应用、默认关闭、按项目开启。否则 agent 拿着你的身份写飞书，就给提示注入开了一条往外传数据的路 |
| 飞书 aily / 智能伙伴 / 豆包工作伙伴 | 不选 | 接入第三方本地 agent 的规格没找到，看起来依赖付费版，而且会把 ash 变成被调用的一方 |
| Claude Code Channels 一类按会话的通道 | 不选 | 绑定在单个正在运行的 claude 会话上，会话不开消息就丢。ash 是多执行器、多任务的调度台 |

## 三、会话模型

| 飞书 | ash | 期次 |
|---|---|---|
| 你和机器人的**单聊** | 你的决策收件箱：所有卡片都发到这里 | P1 |
| 在单聊里**回复某张卡片**（`parent_id` 指向那张卡） | 那个任务：回复提问卡 = 答复；回复其它卡要以 `/reply` 开头才 `POST /tasks/:id/reply`（见第十一节） | P1 |
| 单聊里的普通文本 | 你的助手房间（kind=assistant）。一条飞书消息对应一条 chat 消息，飞书的 `message_id` 直接当消息 id 用：`/chats/:roomId/messages` 对同 id、同内容的重发是幂等的（`server/src/chat/service.ts:74-78`） | P3 |
| 群（在 web 上绑定到一个项目） | 项目群聊（kind=chat）。「@成员 → 建任务开跑」这条链路已经现成 | P4 |
| 群里的话题 | 一个任务。话题根就是那张通知卡：话题里回复提问卡 = 答复；其它卡要以 `/reply` 开头才 = reply（见第十一节） | P4 |

团队执行者的提问是问调度台的，**不推给人**。只推调度台自己的提问。

## 四、出站：推什么，怎么推

### 4.1 推送由数据库对账驱动，总线只负责叫醒

总线不落盘、没有序号，重启空窗里的事件会直接丢。所以：

1. 订阅者照 `watchTaskWrites()` 的写法（`server/src/task-writes.ts:18-27`）。收到事件只记下「某个 taskId 该对账了」，然后 `setImmediate` 入队。**不能在订阅回调里同步读库或抛错**，因为 `bus.publish` 是同步的，异常会冒到 `setTaskStatus` 这类调用方里去。
2. 对账函数从库里算出「这个任务现在要人做什么」，和发件表比对：缺的补发；已经不成立的（在 web 或手机上处理掉了），把原卡片改成「已在别处处理」。
3. 启动时全量对一次账，但要带**水位线**，只补上次在线以后新出现的，或者合并成一张汇总卡，否则重启一次就会刷屏。
4. 发消息时带飞书的 `uuid` 参数（1 小时内同一 uuid 最多成功一次），用发件表的行 id 当 uuid，防止崩溃后重试发出两条。

**「此刻轮到你动手了吗」只算一份。** 一个任务在某一刻要么在自己跑（不用管），要么在等你（回答提问、点验收、处理失败）。界面上那颗「需要你处理」的信号点就是这样算出来的。现在 web 算一份（`web/src/lib/taskAttention.ts`），mobile 抄了一份（`mobile/src/lib/taskTree.ts`），飞书再写第三份的话，迟早会出现飞书说「等你验收」、页面上却不是这样的情况。所以第一步先把它挪进 `shared/` 合成一份，web、mobile、飞书共用。这是纯内部整理，界面行为不变。

举个例子说明为什么非用同一份判据不可：三份草案起初都把「待验收」写成 `stage=awaiting_acceptance`。但自由工作流（默认模式）跑完时 stage 多数是 null，web 的真实判据是「已 done 且没盖过章」（现在在 `shared/src/task-attention.ts` 的 `isTaskAwaitingAcceptance`，注释里记着这一档改过两次的经过）。照草案那样写，大多数任务永远收不到验收卡。

### 4.2 卡片清单

| 卡片 | 什么时候推（按库状态判） | 按钮 → ash API | 期次 |
|---|---|---|---|
| 提问 | `question` 非空，且任务已经 paused（团队调度台例外）。还在 running 时答复会 409（`server/src/task-answer.ts:33`） | 每个选项一个按钮，外加自由作答表单 → `POST /tasks/:id/answer` | P1 |
| 完成待验收 | 任务完成且没验收过（shared 里那份判据）。自由工作流下「完成」和「待验收」是同一张卡 | 「验收通过」（停在中途那道「等我点头」上是「放行，继续下一站」）→ `POST /tasks/:id/accept`。**先回执，再异步执行**，结果靠 patch 卡片回写：合并要排仓库锁、要跑尾段（`server/src/task-accept.ts` 里的 `withRepoLock`、`finishAcceptedTail`），3 秒的回调窗口里做不完 | P1 |
| 失败 | status=failed，或回合起不来 | 「重试」→ `POST /tasks/:id/retry`（只接受 failed） | P1 |
| 已收尾的完成 / 门禁结果 | 完成且已验收或合并，或门禁出结果 | 只做告知，默认推。原地改卡片不会触发推送提醒，所以「完成」一律发新消息，不靠改旧卡 | P1 |
| 驳回待裁定 | 执行者驳回了审查意见 | 三个按钮 → `.../review/dispute/resolution`，带上 `target:{runId, round}`。按钮文案要写清楚：`withdrawn` 的意思是「采纳执行者的说法」，不是「撤回」 | P2 |
| duet 收敛闸 | `duet.gate` | approve / inject。**reject 实际上会取消任务**（`server/src/duet/index.ts:560`），文案必须写「否决并取消」，并且二次确认。闸口带版本号（见 6.4） | P2 |

**每张卡片都带：** 项目名、任务标题、一句「卡在哪」（取自 `GET /sessions/:id/notices`），以及一个打开 ash 的深链 `<base>/?project=<pid>&task=<id>`，`<base>` 在设置里配成 Tailscale 地址。手机不一定连着 Tailscale，多人模式下也未必有登录态，所以**卡片本身必须能独立完成决策**，深链只是补充。

**任何期次都不做成按钮，只给链接：**

- reclaim-turn、kill-cua、删会话消息：由离机签名或真人凭据保护。
- `verify-override`：在「验证 → 合并」这条线上，它会一路推进到合并，不可逆；自由工作流下还直接 409。
- `accept {gate:"skip"}`、`confirmUnverified:true`：都是绕过用户自己设的闸。

### 4.3 不做流式进度

CardKit 的流式模式开启 10 分钟后自动关闭，单张卡片每秒最多 10 次操作，流式和按钮交互互斥。而 ash 的任务经常一跑一小时。更重要的是，推到飞书的内容撤不回来，会话正文可能带着代码和密钥（ash 的「删会话片段」管不到飞书那份副本，见 `server/src/conversation-redact.ts`）。

真要看进度，以后可以做一张「状态卡」，只在状态变化时 patch 一次（单条消息 5 QPS、只能改 14 天内的）。流式最多留给助手回复这种短、有上限的场景。

## 五、入站

1. **先落库再回执，然后异步处理。** 飞书要求 3 秒内处理完，否则会重推。消息按 `message_id` 唯一键去重，官方原话是「不要依赖 event_id」。按钮回调没有自己的 message_id（点的是哪张卡在 `context.open_message_id` 里），按回调顶层的 `event_id` 去重；真正兜底的是信封只能用一次（6.4）。实测回调超过 3 秒飞书**不会**重推，点击就这么丢了，所以回调必须当场回执，不能指望重推补救（见第十节）。
2. **准入默认拒绝**，未授权的消息静默丢弃（见 6.1）。
3. **执行走进程内的完整路由栈，不直接调 service 函数。** 鉴权、可见性、个人面这几道闸都是挂在 `/api/*` 上的中间件（`server/src/index.ts:393-405`）。而 `actorOf()` 取不到身份时会兜底成**管理员**（`server/src/auth/context.ts:63-65`），直接调 service 函数，一旦忘了设身份，就会静默拿到管理员权限。做法是：
   - 用 `app.fetch(req, env)`，身份放进 env。真实网络请求的 env 由 `@hono/node-server` 自己填 `{incoming, outgoing}`，外部伪造不了。
   - 但有 4 处路由会调 `getConnInfo(c)` 读 `c.env.incoming`，包括 `GET /settings`（`server/src/routes.ts:147`）。自己造的 env 进去会直接抛错。所以通道层要带一份**路由白名单**，只放行第四节表格里用到的那几条路由。
4. **斜杠命令做确定性解析**（P3），同时当作卡片按不动时的文本回落：`/answer`、`/reply`、`/retry`，以后再加 `/new`、`/stop`。自然语言不在通道层另做一套 LLM 解析，直接交给现成的助手房间。
5. **附件转两跳**：从飞书下载 → 转成 dataUrl → `POST /uploads` 拿到 `path` → 把 path 放进 `attachments`。

## 六、身份与安全

### 6.1 威胁模型

能给机器人下指令，就等于拿到了这台机器的 shell：agent 手里有 shell，自用模式下所有请求又都是本机管理员。由此推出：

- **自用模式下机器人只属于一个人**：只绑定机主一个 open_id，群功能默认关闭。不能按群 `chat_id` 整体放行。
- **飞书账号从此也是这台机器的凭据。** 如果用公司租户，企业管理员和应用协作者能改应用配置、轮换密钥。个人自用建议在自己建的团队或测试企业下建应用。
- **飞书应用权限压到最小**：只开收单聊（`im:message.p2p_msg:readonly`）、收群里 @（P4 才开）、以机器人身份发消息、更新卡片。不开 `im:message.group_msg`（敏感权限，会读到群里全部对话）、通讯录、文档。这样即使密钥泄露，影响也只限于「冒充机器人收发消息」。
- **消息正文只当数据，不当授权依据。** 授权只看飞书给的 `sender.open_id` 或 `operator.open_id` 映射到的绑定身份。

### 6.2 绑定方向：网页发起，网页确认

1. 在已登录的 ash 网页上点「绑定飞书」，生成一个一次性码（10 分钟有效，库里只存哈希）。
2. 在飞书单聊里把这个码发给机器人，机器人记下发送者的 `(app_id, open_id)`。
3. 回到网页确认：「飞书用户 X 申请绑定到你的账号，确认吗？」

**不能反过来**，让机器人先发码、你去网页上输入：攻击者可以先从机器人那里拿到码，再诱导机主去输。全程也**不经飞书传 ash key**。绑定键用 `(app_id, open_id)`，换应用就要重新绑，这是有意为之。用户被停用时绑定同时失效。

### 6.3 新增一种身份 `im`（实现时提前到 P1，自用模式也用）

在 `ActorKind`（`server/src/auth/context.ts:24`）里新增 `"im"`。加上之后，所有对 kind 的穷举分支都会编译报错，正好逼着把每一处的语义过一遍。它的语义：

- `isAccountHolder` 为 false：账号面的动作（改资料、改 CLI 环境、退出项目）一律碰不到。
- `isAdminActor` 为 false：实例设置碰不到。
- 可见性用绑定用户的 `visibleProjectIds`。
- 聊天路由要显式放行 im，因为现在 `isHumanRequest` 要求 isAccountHolder（`server/src/chat/route-access.ts:29`）。

需要钉住的回归测试：

- 外部 HTTP 无论带什么头，都造不出 im 身份。
- im 身份调 reclaim-turn、kill-cua、`/settings` 写接口一律被拒。
- **通道模块不得引用 `issueHumanActionToken`。** 同进程的代码可以自己签一份真人凭据，这才是真人专属动作的实际风险点。

### 6.4 按钮信封：带代次，存库里

按钮的 value 里只放一个随机、不可猜的信封 id。信封存在 `im_actions` 表里，记录 taskId、动作、收件人 open_id、代次、过期时间和使用时间。回调时依次校验：

1. 信封存在、没过期、没用过；
2. `operator.open_id` 等于信封里的收件人；
3. 代次和当前一致。

校验通过后，按收件人的身份进程内调 API，然后在库里标记已用，重启后也不能重放。

**必须带代次，不能只靠内容键。** `questionKey` 只是 `JSON.stringify([question, options, items])`（`shared/src/questions.ts:86-88`），按内容算，没有代次。agent 原样再问一次「继续吗？」，旧卡片照样能答中新问题。提问的代次可以用提问历史的长度加 updatedAt。duet 闸口原来没有版本号：注入一次意见之后闸口会重新打开，这时点旧卡片上的 approve，就放行了一份你没读过的新方案。现在每开一扇门之前先在库里领一个号（`tasks.duet_gate_version`，`server/src/duet/gate-version.ts`），领不到就不开门。不能从 transcript 里数：开门行只是尽力写，写失败之后再一重启，同一个号就会再发一次（审查第 3 轮实测）。卡上摆的方案也跟着号一起落库（`tasks.duet_gate_shown`，和版本号同一条语句写），卡片按卡上的版本去取，找不到这一扇门的方案就不给「放行」，不拿 transcript 里最近一次开门的正文顶上（审查实测：开门行没写上时，卡上是旧方案，按钮放行的是新方案）。

agent 伪造的卡片上的按钮会因为没有登记过的信封而点不动。但卡片里的链接仍然是钓鱼面，所以**卡片里除了 ash 深链，不放任何外链**。agent 写的文本一律按 plain_text 渲染，剥掉 `<at>`。

### 6.5 密钥与外流

- 凭证放在库文件旁边的 `<db>.feishu.json`，权限 0600，照 handoff 身份文件的做法（`server/src/handoff-identity.ts`）。复制库、做预览快照都带不走它，「不同 ASH_DB 就是不同实例」也自然成立。
- **不进 `app_settings`**：`GET /settings` 会把整份设置回给任何已登录的人，preview-seed 还会把它复制进预览库。
- **不进环境变量**：`agentBaseEnv()` 只在隔离宿主 CLI 那一档才清理环境变量（`server/src/executors/spawn.ts:42-57`），自用模式下所有 agent 都会继承。
- **要如实写给用户的边界**：agent 和 server 是同一个 OS 用户，agent 读得到这个文件，可以冒充机器人发消息。Windows 上 chmod 不生效。缓解手段只有最小权限和一个「轮换密钥」操作。
- **发出去之前过一遍密钥扫描并截断**：失败原因、提问正文都可能是 agent 或命令的原始输出。门禁的 `logTail` 一律不推。另外按项目提供一个「只推标题和链接」的开关。
- **审计**：每个经飞书发起的动作，在任务时间线上写一条旁注「经飞书由 X 执行 Y」，网页刷新后也看得出来源。被拒的尝试也记下来。

## 七、部署与运维

- **不用 SDK**（实现时改的）：长连接协议照官方 `@larksuiteoapi/node-sdk` 1.76.0 的 `WSClient` 逐条对齐，自己实现（`server/src/im/feishu/{frame,ws-client,api}.ts`）。SDK 解包 30MB、带进 axios/protobufjs/lodash，而 server 只要其中一条连接；更要紧的是合并后主仓没重新 `npm install`，引用它的 server 一启动就崩。undici 本来就是 server 的依赖，自带 WebSocket。实测：新版卡片回调以普通 `event` 帧到达，不走 `type=card` 帧；机器人自己加的表情回应也会作为事件推回来，要按操作者把自己过滤掉。
- **启动位置**：放在 listen 成功之后，`startScheduler()` 旁边，复用「预览实例不启动」那个分支（`server/src/index.ts:623-640`）。凭证文件不存在就不启动。`index.ts` 只加一行，逻辑全放进 `server/src/im/`，单文件不超过 700 行。
- **连接状态要持久可见**：显示在 `/api/health` 和设置页上。ash 自己挂了，机器人就会静默下线；ash 默认也没有开机自启。
- **多实例**：飞书长连接是集群模式，同一个应用的多个客户端之间不广播，每条事件只随机给其中一个，而且飞书不告诉你连了几个。所以**一个实例一个应用**：Mac 和 Windows 真机（192.168.1.187）各建一个。预览实例和 `PORT=… ASH_DB=…` 起的测试实例因为拿不到凭证文件，天然不会连。低成本的撞车检测办法：每次连上就给机主发一句「实例 <指纹> 已上线」。
- **丢事件**：长连接会静默丢事件（cc-connect 踩过）。出站靠对账兜底；入站的按钮点击丢了，用户再点一次即可，信封保证幂等。
- **事件循环**：长连接心跳和整个 server 共用一个事件循环。Windows 上出过 node-pty 卡死主线程的事故，那种情况下机器人会被飞书判离线。适配器接口设计成纯消息传递，将来需要的话可以整体挪进 worker 线程。碰了 win32 分支就上真机跑一遍。
- **配额**：同一个群里所有机器人共享 5 QPS，同一用户也是 5 QPS，由发件表限流。免费版自建应用的 API 月配额是 **1 万次**（用户 2026-11-06 在开发者后台核实）。开放平台没有查询配额的接口，所以每次调用都自己记账、按用途分档降级，见第十一节。
- **飞书侧开通顺序**：自建应用的权限和事件订阅每改一次都要发版，部分权限要企业管理员审核。后台保存「长连接」订阅方式时本地程序必须已经连上，所以要先在 ash 里配好凭证、连上，再去控制台保存。

## 十、第零期实测结论（2026-11-06）

用一次性探针连真实应用「ash 助手」，在单聊里发消息、点一张 JSON 2.0 测试卡片上的按钮。SDK 是 `@larksuiteoapi/node-sdk` 1.76.0，飞书国内版。

| 验证项 | 结果 | 对方案的影响 |
|---|---|---|
| 卡片按钮回调能否经长连接到达 | **能。** 5 次点击全部以 `type=event` 帧到达，没出现过 `type=card` 帧。SDK README 里「长连接不支持回调」的说法已过时 | 用 SDK 的 `EventDispatcher` 就行，不用自己解帧 |
| 回调里有什么 | 顶层就是这些字段（SDK 已把 header 和 event 拍平）：`schema, event_id, token, create_time, event_type, tenant_key, app_id, operator{open_id, union_id, tenant_key}, action{value, form_value}, host, context{open_message_id, open_chat_id}` | 信封校验用 `operator.open_id`；点的是哪张卡用 `context.open_message_id`；去重用 `event_id` |
| 自由作答表单 | 能。`action.form_value` 形如 `{"answer":"…"}`，键是 input 的 `name` | 提问卡的自由作答直接用表单 |
| 先回执、后改卡 | 能。回调里先回「处理中」，6 秒后用 `PATCH /im/v1/messages/:id` 改卡，返回 code 0。不需要回调里那个 30 分钟内最多用 2 次的延时更新 token | 验收这类慢动作：回调先回执，结果一律走 patch。改卡次数只受「单条消息 5 QPS、14 天内」限制 |
| 回执超过 3 秒 | 回调 4 秒才回，飞书**没有重推**（只来了 1 帧）。8 秒后再 patch 照样成功 | 超时的点击会丢，不会重来。回调里只做毫秒级的信封校验和入队，其余全部异步 |
| 发消息带同一个 `uuid` 连发两次 | 两次都返回 code 0、**同一个** message_id，只发出一条 | 发件表重试时带同一个 uuid 就能放心重发，不会重复推送 |
| 表情回执 | 能（code 0），收到消息后约 0.6 秒加上 | 「已收到」回执可行 |
| 发送者身份 | 有 `open_id`、`union_id`；没开通讯录权限时 `user_id` 为 null | 绑定键按原计划用 `(app_id, open_id)` |
| 回读消息内容 | `GET /im/v1/messages/:id` 对 2.0 卡片只返回一段降级提示文字（「请升级至最新版本客户端」） | 卡片现在长什么样只能 ash 自己记在发件表里，不能回读飞书 |
| 延迟 | 回调帧到达处理函数约 1 毫秒；发一张卡约 0.4 秒 | 3 秒窗口很宽裕 |

另外顺带收到三种事件：用户进入单聊（`im.chat.access_event.bot_p2p_chat_entered_v1`）、消息已读（`im.message.message_read_v1`）、机器人自己加的表情（`im.message.reaction.created_v1`）。P1 只订阅需要的事件，多余的从后台去掉。

后来补上的两条：同步回卡在手机上确实生效（用户看到卡片上的文字变了）；免费版 API 月配额是 1 万次。

## 十一、实现说明（2026-11-06）

P0' 到 P4 一次做完，代码在 `server/src/im/`（飞书协议在 `feishu/` 子目录，其余与平台无关）、`server/src/auth/im-actor.ts`、`server/src/db/schema-im.ts`，网页在设置 → 飞书。每个文件头部注释写了「为什么这么写」，这里只记与方案稿不同的地方和实测结论。

**与方案稿的出入**

- 不用 SDK，见第七节。
- `im` 身份提前到 P1、自用模式也用：卡片按钮和消息都以「绑定者的 im 身份」经 `app.fetch` 走完整路由栈。im 身份只能调白名单里的路由（`auth/im-actor.ts`），验收不能带 `gate` 或 `confirmUnverified`，角色一律按 member 算。
- 「此刻要人做哪一件事」是 `shared/src/task-attention.ts` 的 `humanTurnOf`：一个任务一刻只推一张卡。下一步变了，旧卡改成「已处理」，新卡另发。
- 启动刷屏没有用水位线，用的是「积压超过 5 张只推一张汇总卡」，汇总卡上点「逐张推给我」每次放 5 张。
- 推送仍由总线事件叫醒对账，另有十分钟一次全量对账兜底。归档、取回、删任务、删项目，以及停用 / 恢复账号、改角色、增删项目成员，都直接改库、不发总线事件，`im/routes.ts` 的 `mountImSweeps` 给这几条路由包了一层，成功后立刻整盘对一次账（实测发现：不包的话网页上归档后，飞书里的卡要等最多十分钟才收起）。
- 回调里能当场改完的卡（点击结果、按钮失效）一律走同步回卡：不经 API，不花额度。慢的（验收合并、建任务、停任务）先回「处理中」，结果再 patch；没办成就把原卡改回去、按钮放回能再点，原因回在卡下（这条回复和结果回写同一个额度用途，额度见底也发）。收尾在拼「处理中」卡之前就挂上：拼那张卡要读库，读失败只少回一张卡，已经起跑的那件事照样落下结局（审查实测：这一步抛错，停止办成了，卡却永远停在原样）；结局落库失败就一直退避重试，不撒手等重启。
- 卡面有两条互不排序的写入路：回执里带回去的卡（结果卡、「处理中」、「已过时」）和发件队列的改卡，飞书上谁后到显示谁。约定库里那份是卡上最终该有的样子、最后落到卡上的必须是它（`im/actions.ts` 文件头）：回执发出（或没发出）之后对一次（`acknowledged`）——那一下的事还在办就不动，结局落库后排的改卡一定在回执之后；否则带回去的不是库里那份、或者没送到，就再排一次改卡（审查实测：结局在拼「处理中」期间落了库、改卡先到，「处理中」随回执后到，卡永久停在「处理中」）；带回去的就是库里那份并且送到了，不另花一次改卡。发件队列改出去的是旧的那份（改卡期间库里换了）时同样再补一次（`outbox.ts` patchOne）。回执之后间隔几百毫秒的改卡在飞书上按什么先后生效没在真租户测过，P0 测的是 6 秒。
- 卡片代次只说明「还是那件事」，不说明卡面还对：每张决策卡另记一个渲染指纹，标题、深链、只推标题这些变了就原地重渲染。
- 发件授权按行记、在出口现核（审查第 2 轮指出：按「有没有挂任务」决定查不查，助手回复、汇总卡、确认卡、/todo 都漏过去了，改卡也没查）。`im_outbox` 每一行入队时记下 `scope`：不含 ash 数据的静态句是 system；回给发话人的、他自己这次操作的结局（接口报错、投不进房间、拿不到回复）是 reply，出口不再核他此刻能不能看、任务和房间还在不在（报错说的常常正是这件事，照核就永远发不出去），只核群还绑着那个项目、项目是不是只推标题；其余按内容来源记 task / project / principal / room / digest，并盖上收件去处那一次绑定的 `boundAt`。发出、改卡、回调回执里直接带回去的卡三个出口都按它现算（`im/scope.ts`、`im/exits.ts`）：发不了的作废；已经发出去的卡改成一张写着原因的中性收起卡；项目此刻设成只推标题、这一行又备着短的那一版，就换成短的。收回内容的这两种改卡按结果回写的用途发，额度见底也照改。task 只认此刻的资格（换了绑定的人此刻看得见就照发），替某一个人做出来的（个人信息、房间回复、确认卡）换了绑定就不给。只推标题管的是推送、通知和按钮的结果 / 报错；助手和群聊房间里的对话回复是他自己问出来的，不受这个开关影响。
- 直接回复不是提问的卡（失败卡、待验收卡、通知）不再当成给任务发消息，要以 `/reply` 开头（用户 2026-11-06 选定）：送到之前任务可能刚问了一道新题，这句话会顶掉它。网页对话框没有这一层，行为不变。
- 回复提问卡（带不带附件）一律走答复接口，带上卡片代次 `questionOccurrence`；答复接口在写入那一刻核它（`task-wait-ownership.ts` 的 `questionOccurrenceOf`：提问占位 id，老数据退回「第几次提问 + 题面指纹」），同样的题面再问一次，旧卡上的回复也答不中。附件随答复进那一轮。
- 按钮的结局一个事务落库：信封的结局、卡上该显示的样子、待改卡标记（没办成时连同原因回复）一起提交，中途退出就整笔没发生，重启后 `recover()` 按现状接管。结果卡随回执带回去的那一路先记 `acking`：回执在 2.7 秒内发出才算送到；没确认的（长连接断了、进程退出了）15 秒后照样改一次卡。
- 验收、重试按钮带着卡上那一版成果 / 那一次失败进核心接口（`task-result-version.ts`：成果 = 这一版的结束时刻，团队取执行者里最晚结束的、和调度台自己最近一轮开始的那个里更晚的一个——调度台每轮收尾落回 idle、结束时刻一直空着，只能从它的回合记录认；失败 = 那一次失败的结束时刻），接口在拿到验收互斥 / 回合占位之后现核，对不上就不办，卡上说明（自由审查第 1 轮实测：卡片代次核过之后、请求进验收之前另一端又跑完一轮，验收的是没给人看过的新成果）。设了验收前置命令时，这份期望值跟着验收选项落进门禁记录，门禁绿了之后的自动验收照样核它。回复失败卡发 `/retry` 同样带着；不是回在失败卡上的 `/retry` 不猜要重试哪一次。网页和 MCP 不传期望值，行为不变。
- 预设工作流上的「等我点头」另有一份关口身份（`tasks.human_gate_id`，`task-human-gate.ts`）：线每走到一道关，在挪游标的同一条语句里领一个新的（接力导入时停在关口上的也重新领，离开期间本机发出的卡一律落空）；游标停在关口上的时候，待验收卡的代次是「成果身份 + 关口身份」，不在关口上只有成果身份（和加列之前发出的卡同形，老卡照旧有效）。放行之后、走到下一站之前游标还在这一道上，身份不变：那一段不冒新卡，同一道关的卡再点也不放第二遍（不然后面那一段的命令会并着再跑一遍）。中途那几道放行只挪游标、不起新的一轮，成果身份前后一样，只认它的话上一道关的旧卡能放行后来那一道，点过上一道的卡之后下一道关也被那张已处理的卡占着、发不出新卡（自由审查第 1 轮实测两条都复现）。按钮带着关口身份进验收接口（`expectedHumanGate`），接口在验收互斥里现核；放行那一步按「游标、阶段、关口身份还是核过的那一份」条件写，核过之后线才换了关就落空；门禁绿了之后的自动验收也带着它。卡上的说法跟着关口走：中途那道写「放行，继续下一站」、确认框和网页确认框同一句（`shared/src/accept-message.ts`），不提合并和门禁；最后一道写「验收通过」。结果和完成通知照接口实际做的说：放行、就地验收、只记认可、只打标签、合进工作区没提交、合并各说各的，尾段没跑成、清理有提醒、验收前自动提交了另说一句；只推标题的项目确认框不带分支名，尾段原因、自动提交原因换成不带原话的那一句。
- 团队验收从进门到盖章（含发布尾段）占住全队（`team-acceptance-hold.ts`，审查第 2 轮实测：只锁调度台，进门核过版本之后执行者照样起跑、改共享目录，验收合进去的是谁都没看过的一版）。用起跑同一把回合锁占住调度台、共享执行者，团队有自己的 worktree 时连这个目录里其余的共用者一起；占着的时候它们起不了新的一轮，改状态 / mode、重新排队、删除归档、写工作区（带 force 也不行）、往团队里加执行者或审查都 409 并说明「所属团队正在验收」，验收自己的守卫和自动提交认得这份占位。调度台的回合不走那把锁，由投递口挡：写进它 stdin 之前、离线开台之前都先问；挡下的用户插话回待发送托盘，执行者汇报进持久待送队列，验收结束补送（调度台离线的补开一次台）。它自己 CLI 起的回合挡不住，所以占住时记下成果版本，之后每道守卫和盖章之前各核一次，变了就不验收（已经合并的照实保留）。网页、MCP、飞书三个入口同一套。
- 同一个人同时发来几句、各自发现还没有房间时会各建一间：建好之后按「映射还是我读到的那一间、绑定还是入口读到的那一次」原子领取（`claimGroupRoom` / `claimAssistantRoom`），只有一间领得到，其余的改用胜出的那间、删掉自己建的。群这期间解绑重绑、换了项目，这一句不投、请他再发一次，旧绑定下建的房间不落进新绑定的映射。出口那道「只放行映射上的那一间」不动。
- 「完成也推」的验收、门禁结果通知按任务的结局账发（`im_outcomes`，`im/outcomes.ts`）：每次对账现算「最近一次验收是哪一次」（每次落章生成一个 `acceptance_id`，merged → accepted 是同一次、沿用；摘牌清掉，原样挂回的还是同一次、连 id 一起挂回；团队验收联动的执行者各自一个；接力随任务带走。不拿结束时刻：验收之后问一句、跑一次旁路回合都会改它。加列之前验收的老行退回按落章事实拼，事后补齐合并事实时最多多推一次）「最近一次跑出结果的门禁是哪一次、过没过」，跟账上比，变了就发一条新的文字消息，有这个人的待验收卡就回复在它下面。事件丢了（重启正好落在对账前）由全量对账按「账和现状对不上」把这些任务带上补发。不看决策卡收没收起（审查实测：飞书上点验收成功时卡先被按钮的结果收起，原来以卡为判据的那条通知一条也发不出）。第一次看到的任务只记账不补推；开关关着也照记账，再打开不补推关着期间的；团队执行者、归档、接力出去的不发。「任务完成」那一下就是待验收卡本身（新卡就是一条新消息），不另发。
- 读失败只当「这一下没读到」，不当「没有」（审查第 2 轮实测：一次 500 被当成房间没了，换掉了还在的房间，旧房间里的回复从此发不回来）。ash 接口的失败分四种（`im/ash-client.ts` `failureOf`）：404 没有（或看不到）、403 被拒、其它 4xx 不收、5xx 和没调通算瞬时。只有 404 和房间换了项目才另建房间、换映射；瞬时失败这句不投、请他再发，映射原样。投进房间报瞬时失败或 409 时先重读房间核实这句在不在；等回复时读不到房间下一圈再看，等满 20 分钟还读不到才说。项目列表、建任务这些读不到也照实说「这一下没读到」、建没建成说不确定，不说「没有项目」「没建成」。飞书这一侧：取 token 失败不算这一行发失败，推迟 5 分钟再发、不耗重试次数，状态页显示原因；回复的锚点消息撤回 / 删了 / 看不到（`230011` `230019` `230050` `230111`）改成直接发到原会话；非 JSON 响应一律可重试；长连接只有 403、514 停手，其余（含连接数超限）退避重连。凭证文件、存着的选项读坏了就停推、在状态页报出来，不拿默认值顶上（选项坏了默认值里的「开着」会把关掉的通道拉起来）；凭证文件只是这一下读不了（不是不在、不是坏了）过一分钟自己再起。库里自己存的东西也一样：按钮记录坏了拒掉这一下（空着去验收就成了不核版本），飞书传来的正文解析不了叫他重发、不当空消息吞掉，发件队列里一行坏的标成放弃、不卡住后面的；机器人身份没查到每分钟重查一次。
- 群设置里同一个项目好几个群都开着推送时，只有最近绑的那个收卡，其余的会标出来；别人绑的群看得见、改不了（按钮置灰），跟接口的拦法一致。
- 改 / 解绑 / 用码覆盖一个已绑的群，资格是同一条（`server/src/im/groups.ts` editRefusal）：看得见它此刻的项目，并且是绑它的人或实例管理员。判资格读到的绑定人、项目、绑定时间在写入的同一个事务里再核一次（sameGrant，群聊房间认领也用它），对不上就整笔不写、回 409 请他刷新：码不翻，群聊房间映射也不清。两轮审查各实测一条：两个人同时确认同一个群，后提交的覆盖了前一个；群被管理员移到你看不到的项目之后，你先前发出的「开推送」照样打开了新项目的推送。
- 飞书选项（总开关、完成也推、深链、月额度、只推标题）的读改写在 `im/meta.ts` 里排成一队，保存接口拿队里紧挨着的上一份判断要不要重启通道、改卡（审查实测：两个页面同时保存，一个勾「只推标题」、一个改月额度，两边都回成功，前一个勾选被整份覆盖掉）。
- 去重标记同时是可恢复的执行进度：消息先连原文落库再回执，重启后没办完的照原文重办（正要答复 / 发给任务的那一步不幂等，不重办、照实告诉用户）；点了一半的按钮按现状判办成没有，没变就放回去，变了就记完收卡。

**月额度 1 万次的分档**（`im/quota.ts` 头部有完整表）：每次调用前按用途过闸。用到 70% 起不加「已收到」表情；90% 起只发决策卡、对话回复、附件下载和结果回写；99% 起只剩「你刚点的那一下」的结果回写。按北京时间切月。设置页显示本月用量和按种类的明细。

**实测抓到的问题**

- 卡片 JSON 2.0 的输入框 `max_length` 上限是 1000，超了整张卡会被拒（`230099`，`ErrCode: 11310`）。现在封顶 1000，回归测试钉住。写得长的答复请直接回复那张卡片。
- 一次联调大约用 18 次调用：取 token 3 次、查机器人信息 1 次、发卡 7 次、改卡 7 次。

**没覆盖的**

- 预设工作流停在「人工」站点（`awaiting_review`）时不推卡：它在判据里算「机器在动」，按钮也没有对应的路由。
- `stage=verify_failed` 只发通知、不给按钮，原因见 4.2 末尾。
- `test:im` 没有加进验收前置命令 `test:accept`，是否加由用户决定。它全程用假的开放平台，不连真飞书。

**飞书后台的开通顺序**：在 ash 设置里保存凭证，等状态变成「已连接」→ 去开发者后台，事件订阅方式选长连接，订阅 `im.message.receive_v1`、回调 `card.action.trigger` → 权限开 `im:message.p2p_msg:readonly`、`im:message:send_as_bot`；要用群再开 `im:message.group_at_msg:readonly`，要收图片和文件再开 `im:resource` → 发版。设置页的「开通顺序」写的是同一份。
