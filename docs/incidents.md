# 事故档案

这里存的是根 `CLAUDE.md` 里那些约定的**来由**：踩过的坑、实测复现出来的现象、试过且被证伪的路。

分工是明确的——**规则本体留在 `CLAUDE.md`**（那是每次动手前都要读一遍的东西），**事故经过放这里**（那是想知道「为什么非得这么写」「这条能不能改」时才翻的）。

搬迁原则：**整段原文迁移，不压缩、不改写**。这些踩坑记录是这个仓库最贵的资产，压缩掉的一定是「为什么」，而那正是唯一不可再生的部分。

## 僵尸调度器：明明确认了却记 failed（2026-07-27）

对应约定：`CLAUDE.md` 的「完成确认**同时落库**」。

## 停止全组：后端全做对了，用户却只能得出「按钮坏了」（2026-07-27）

对应约定：`CLAUDE.md` 的「停止/暂停类操作必须在 UI 上留下持久可见的状态」。

点「停止全组」后端全做对了——进程 SIGTERM、内部组置 `paused`、会话写入系统提示——但按钮原样、状态徽标不动、`paused` 前端压根没渲染，用户只能得出「按钮坏了」。

更坏的是它**掩盖了真问题**：界面若明说「已停止，0 个执行者被打断（都已完成）」，用户立刻就知道还在动的鼠标不归 ash 管，而不是把一个架构缺口误报成 UI bug。

## CUA 旁路会话：ash 够不着的全局单例（2026-07-27）

对应约定：`CLAUDE.md` 的「三层击杀只覆盖 ash 自己 spawn 的进程树」。

codex 的 computer use 由 `/Applications/ChatGPT.app` 侧拉起 `SkyComputerUseService`（**开机级全局单例**，跟着宿主 App 一起启动，不是每任务一个），ash 的进程组/fd/ppid 三条线索一条都够不着它。

**已验证有效的手段**：`stopTask` 三层击杀掉执行者后，`SkyComputerUseService` 随即消失，屏幕指示器跟着走（CUA 服务有 `shouldTerminateWhenNoClientsRemain` 语义，codex 客户端一死它就自行退出）。

**已被实测证伪、别再试的路**：`SkyComputerUseClient turn-ended`。在**活跃** CUA 会话上手动调过 4 种 payload（`thread_id` 用真实 `cliSessionId`、加空 `turn_id`、`codex.app_session_id`、`threadID`），**全部 `exit 0` 且毫无效果**，服务照活、执行者照常截图；那个 CLI 对任何输入（包括非 JSON）都静默返回 0，「成功」是假象。

**仍未验证的一条**：agent **正常完成**（而非被杀）时服务会不会残留——两次对照实验都因 codex 选择用 Orca 截屏而没能触发 CUA，**别把「没验到」说成「不会发生」**。

**清理盲区**：`pauseGroup` 只处理 `running`/`queued` 成员，已 `done` 执行者遗留的旁路会话没人管——2026-07-27 用户点「停止全组」时执行者早已全部 done，鼠标却还在屏幕上动。

## 端口撞车产幽灵：不占端口、但调度器在轮询生产库（2026-07-27）

对应约定：`CLAUDE.md` 的「启动期的致命错误必须 `exit(1)`」「同一个数据库文件同一时刻只允许一个 server」。

单实例守卫只挡「同一个 DB」，**端口撞车是另一条产幽灵的路**：`PORT=4317 ASH_DB=/tmp/x.db` 能顺利拿到 DB 锁，然后在 listen 那步撞死；旧代码里 scheduler 已经先起来了，EADDRINUSE 又被通用兜底接住只打日志不退出，于是留下「没有端口、但调度器在轮询生产 DB」的活死人。

实测复现：修复前第二个实例在 EADDRINUSE 后照样存活并 `scheduler started`；修复后 exit 1、日志里 `scheduler started` 出现 0 次。

而「不同 DB 并存」是既定的 throwaway 验证工作流，不能靠收紧锁粒度来解决。

同源的另一个现象：第二个实例**不占端口所以 `lsof` 查不出来**——2026-07-27 实测发现一个 7 月 22 日起的幽灵实例活了 5 天没人发现。

## 没有监听者的 `'error'` 把任务永久卡在 running（2026-07-28）

对应约定：`CLAUDE.md` 的「预检失败的 `'error'` 事件不能立刻 emit」。

抢在订阅者挂上之前 emit `'error'`，EventEmitter 直接升级成 uncaughtException，被运行期兜底一吞，run loop 就永远等不到 `done`：**任务卡死在 running、`stopTask` 返回 true 却停不掉、再发消息被 409 挡回，只有重启才能解**。

复现方式：在一个 worktree 已被删除的任务里回复即可。

## 只改数据库不停进程的三连错（2026-07-21）

对应约定：`CLAUDE.md` 的「取消/打断任务的唯一正道是 `stop_task`」。

对 running/queued 任务 PATCH status 只改数据库不停进程，会三连错：canceled 提前推进队列（串行变并行）、活着的 agent 调 `complete_task` 吃 409、结算把 canceled 覆盖成 failed。

详见 codex 线程 `019f8d03`。也因此失败告警文案不指控「agent 未调用」——确认也可能是被 409 拒掉的。

## 并行验收互相拆台：同一个工作区两个 merge

对应约定：`CLAUDE.md` 的「同一仓库的写型 git 操作全局串行」。

一个仓库的 `.git` 是所有 worktree 共用的单一状态机，并行写有三种拆台方式：

1. 并行验收里 A 读到 target=X 决定 FF、B 抢先把 target 推到 Y，A 就报 `fast_forward_failed`；
2. 目标分支恰好检出在项目目录时（最常见的 `main`）FF 走不通会退化成**在项目工作区里 `git merge`**，两个验收同时进到这一步 = 同一个工作区两个 merge，实测直接 `Unable to create '.git/index.lock': File exists`；
3. 更坏的情况是 B 失败后的 `merge --abort` 把 A 已完成的合并回滚掉。

## CLAUDE.md 自己的膨胀史（2026-07-29）

对应约定：`CLAUDE.md` 顶部的「新约定按升级顺序找地方放」，以及 `.githooks/pre-commit` 的体积闸。

逐提交量出来的曲线：

```
2026-07-27  14,020 字节
2026-07-28  24,122 → 34,720
2026-07-29  35,409 → 41,142
```

三天 ×2.9，日均 +9k 字节 ≈ +2.7k token/天，57 次提交里只有 3 次是净减少（还都是删功能带的）。

三笔额外的账：

- **token 税**：41,142 字节 ≈ 12.5k token，每个 claude 执行器每轮都付。
- **冲突热区**：一个全局单点、append-only、没有天然分片的 40+ 项列表，配上 N 个并行 worktree agent，冲突是必然的——某次验收循环里撞了 3 次合并冲突，冲突文件**全部只有 CLAUDE.md**，代码文件零冲突。
- **对 codex 从来没生效过**：codex 读的是 `AGENTS.md`，而根目录没有这个文件。`mobile/` 里两份都有（`mobile/AGENTS.md` 是正文，`mobile/CLAUDE.md` 只有一行 `@AGENTS.md` 指过去）——这个仓库自己已经解过这道题了，根目录漏了。而系统并没有因此崩掉，这反过来证明真正在约束 agent 的是做进系统的那部分：`complete_task` 的 prompt 前言注入、running 状态 PATCH 的 409 硬拦、`resolveExecutorFor` 的 API 形状。

根因不是「攒多了该清一次」，是**成本外部化**：加一条 CLAUDE.md 成本 2 分钟、当场生效、写进交付总结还显得周到，收益全归本轮 agent；而账单落在下一个 agent 的入场费和下一次并行冲突上，那时加条目的 agent 早已验收走人。原元规则只说「值得就主动补一条」，全文没有任何一句奖励「搬走一条」或「做进系统」。

所以修的是激励而不是劝自觉：把账单送回产生成本的那一刻（commit），并让「减」和「加」一样可见。

## 关口画在验证前面就被跳过（2026-08-05）

对应约定：`server/CLAUDE.md` 的「执行者彻底退出自我验证 / 就地验证」一条，以及推进器文件头（`server/src/workflow-advance.ts`）那三条不变量。回归：`npm -w server run test:workflow-gate`、`npm -w web run test:workflow-rail`。

用户的原话是「等我点头这一步都没等我去打开预览瞅一眼，点个确认或补充点信息，就自动开始第四步的自动验证了」。任务 `bq3PLDuZzZOt` 的线是 **干活 → 打开预览 → 等我点头 → 自动验证 → 合并并清理**，关口画在验证**前面**。执行记录里的证据链：

```
06:29:46.311  预览已起
06:29:46.317  stage=verifying          ← 关口零停留，相差 6 毫秒
06:56:48      时间线原话：「这条线上没写「等我点头」，走到「合并并清理」就自己合了。」
```

`tasks.workflow_at` 全程为 **null**，而线上明明画着 human 站——最后那句时间线是这次事故最有价值的一行：系统不是「忘了停」，是**真心认为这条线没写关口**。

根因有两层，都在「按锚点类型读线」这个旧模型里：

1. 旧推进器按锚点**类型**决定下一步，顺序写死成「验证 → 关口 → 合并」，用户画的顺序根本没人读；
2. `workflowPolicy.humanGate` 当时的判据是「有 human 站**且排在 verify 之后**」，于是关口画在前面时整条线被判成「没写等我点头」，一路自动验证 + 自动合并到底。

第二期把段落切分改成按**站 id** 走（游标 `tasks.workflow_at`）之后，服务端这条路已经修好；但同一次排查里发现另外三处仍活着的同类错误，它们跟 dist 新旧无关：

- **前端游标没跟着换**（`web/src/workflow/workflowModel.ts`）：文件头当时写着「第二期落了真游标就换掉这里」，游标落了、这里没换，仍从 stage 反推。`stage=verifying` 时反推指向 verify 站，排在它前面的 human 站于是被画成「✓ 已过」——用户看到的是「我压根没点头，它却说我点过了」。
- **关口按钮只看 stage**（`WorkflowInspector.tsx` 的 `atHumanGate`）：`awaiting_acceptance` 只说明有人把任务标成了待验收，可能是 agent 按完成协议自报的，也可能属于线上**另一道**关口。照它给按钮，用户会在一道还没轮到的关口上按下不可逆的验收。
- **关口静默停下**（`server/src/review.ts` 的 `enterHumanGate`）：stage 已是 `awaiting_acceptance`（agent 自报）时整个函数直接 return，那句「这条线走到「等我点头」」的时间线一个字都不写。任务停着不动，用户无从判断它是在等自己点头还是卡住了——这正是「停止/暂停必须留下持久可见的状态」那条规则的同一种病。

三条推论：

- **「线上有没有这一站」和「此刻停在哪一站」是两个问题**，前者读定义、后者读游标，任何一处拿 stage 当站的代名词都会重犯这次的错。
- 用户能把站排成任意顺序，就不能有任何一处代码假设某种顺序；`SINGLETON_KINDS` 那种「同类站只能有一个」的限制也是同一个假设的产物。
- 这次真正的证据不是那张截图，是执行记录里 6 毫秒的间隔和那句「这条线上没写等我点头」。**用户报「流程没走对」时，先去翻那条任务的时间线**，比读代码推断快一个量级。

### 第二段：关口停下来了，一点验收又把验证站跳了（同日）

上面四处修完，用户在**同一条线**上再跑一次：关口这次真停住了（时间线写出了「这条线走到「等我点头」，停在待验收等你决定。」），他点了「验收通过」，然后：

```
开始验收：按线上写的「安全合并（仓库锁内）、删 worktree 和任务分支」处理，目标 feat/issue-center
已合并 (merged) → 合并完成（纯 fast-forward）→ 清理完成 → 验收完成 (accepted)
```

线上「等我点头」和「合并并清理」之间画着的那站 **「自动验证」从没跑过，线路图上却显示它已过**（前端如实反映后端：stage=accepted 就是整条走完，这一处不是 bug）。

根因是**同一个错误模型的第五处**，藏在 `isFinalHumanGate`（`shared/src/workflow-policy.ts`）里：

```ts
return !def.steps.slice(idx + 1).some((step) => step.kind === "human");   // ← 只数 human
```

判据是「这道关口后面还有没有**别的等我点头**」。用户这条线只有一道关口 → 判成最终关口 → `task-accept.ts` 那个 `if (!isFinalHumanGate(...))` 的放行分支进不去 → 直接走最终验收 → `runAcceptedTail(skipAccept: true)` 合并清理，**中间的 verify 站被整站跳过**。「最后一道关口 = 这条线的终点」这个假设，只在关口画在末尾时成立。

改成 **`nextAnchor(def, at) === null`**（后面还有没有**任何**会停下来的站）。新判据是旧判据的超集——后面还有 human 站时它必然也是锚点，所以既有的多关口用例一字未改：

| 线 | 在那道关口点验收 |
|---|---|
| 干活 → 等我点头 → 验证 → 合并 | **放行**，游标去验证站（本次修复） |
| 干活 → 验证 → 等我点头 → 合并 | 最终验收，合并清理（不变） |
| 干活 → 点头A → 点头B → 合并 | A 放行、B 最终（不变） |
| 干活 → 等我点头 → 验证（无合并站） | 放行 → 验证 → 线走完，不合并 |

两条推论：

- **一个判断有几处实现，就要有几盏红灯**。推进器那条路修好之后，`acceptTask` 这条路上同名的判断仍是旧的：`test-workflow-gate.ts` 当时只测推进器，全绿，而用户点下去的正是没测的那条。所以这次的回归直接在真库 + 真 git 仓库上调 `acceptTask`，断言 main 的 ref 一动没动、worktree 还在、分支还在。
- **worktree 里没有 `node_modules`，`@ash/shared` 会解析到主仓那份**（本次首跑就是这么撞出来的：改完 shared 测试照红，因为 server 读的是主仓的旧文件）。改 shared 时先 `ln -sfn ../../shared node_modules/@ash/shared`，否则验证的是别的分支的代码。

## 排队消息凭空消失：被单飞锁静默吞掉（2026-08-07）

对应约定：`server/src/pending-messages.ts` 文件头那条「一旦 claim 成 sent 就必须真的进到会话里」，以及 `continueTask` 的布尔返回值。回归：`npm -w server run test:scheduled-messages`。

用户的原话是「我刚才好像在一个任务里发了一个排队的任务，但是不知道是切了几次会话或刷新页面的原因，还是重启了服务的原因，现在找不到那个排队的消息了」。**三个猜测全不成立**：消息既没被刷新弄丢，也跟重启无关，它是被后端悄悄吃了。

库里的证据链精确到毫秒（任务 `1rojF5Tjau91`，消息 `bwaiaJm7J84t`）：

```
06:10:02.366  用户在运行中的任务里发话 → scheduled_messages 落一条 mode=queued/status=pending
06:14:04.271  sessions.ended_at —— agent 这一轮结束
06:14:04.281  scheduled_messages.sent_at —— 终态钩子抢下这条消息，标成 sent（+10ms）
06:14:04.316  时间线还在写结算产物（+45ms，说明 run loop 的 try 还没走完）
              ……此后 sessions.turn_started_at 再没变过：**没有任何一轮为这条消息跑起来**
```

根因是一条早就写在 `server/src/runs.ts` 文件头、却没人在这条链路上遵守的规矩：**结算钩子跑在 run loop 的 `try` 里，那一刻单飞锁还锁着**。`setTaskStatus` → `flushPendingForTask` → `deliverPendingMessages` 先原子地把消息 `pending → sent`（防两个触发源重发），紧接着 `void continueTask(...)`，而 `continueTask` 第一句就是 `if (!claimTurn(taskId)) return;` —— 抢不到锁，直接返回，什么都不发生。

于是这条消息同时从**两个**地方消失：托盘只显示 `pending`，它已经是 `sent` 了；会话时间线里从没写过这一轮。用户手上一点痕迹都不剩，连「我确实发过」都无从证明——这比报个错坏得多。

两处让它变得更难发现的细节：

- `runs.ts` 里其实早就备好了唯一安全写法 `continueWhenIdle`（由 `releaseTurn` 同一处排空），注释甚至写明了「直接 `continueTask` 会被静默挡回」。就地验证轮用了它，排队消息这条链路没用——**规矩只写在注释里，就只能保护读过那段注释的人**。
- `test-scheduled-messages.ts` 里已有一条「排队追问」的用例，而且它是绿的：它直接调 `setTaskStatus(taskId, "done")`，**锁在测试里根本没锁上**。测试复刻了调用顺序，没复刻并发状态，于是格子看着覆盖了、真实链路一次都没走过。

三层修法，缺一层都还能漏：

1. **投递等锁退干净**：单任务分支改走 `whenTurnIdle`，另加一个 `inFlight` 集合——冷却窗口只有 5 秒，而「等一轮跑完」可能是几十分钟，这段时间里同一任务的第二条消息绝不能也被抢下来。
2. **`continueTask` 返回 `boolean`**：`false` 只有一个来源——被单飞锁挡回、这句话一个字没送出去。把「跑完了」和「压根没跑」在类型上分开，所有拿着用户原话的调用方（`/reply` 的立刻发、`/answer`）都据此兜底：原样落成一条排队消息，任务空下来照发。
3. **实在送不出去也要留底**：`cancelPendingMessage` 把**原文**一并抄进时间线。取消意味着它从托盘上消失，不留原文用户就只能凭记忆重打一遍。

回归用例直接把锁锁上（`claimTurn` → `setTaskStatus` → `releaseTurn`）复现了 2026-08-07 这一格：锁着时不许起下一轮，锁一放必须把原话落进会话时间线。改回旧写法它当场变红。

补一句同源的坑（同日发现）：第一版修法是「先认领成 `sent` → 再等锁退干净 → 才真送进会话」，等待是**内存里的回调**。服务恰好在这几秒里重启，行已是 `sent`、回调随进程一起没了 —— 同一个消息消失，触发条件从「锁」换成「重启」，而且窗口比原来还宽。所以认领必须留到**真要送的那一刻**（`deliverWhenIdle`）：等待期间那一行保持 `pending`，最坏情况只是晚发一会儿——开机第一次 tick（`startScheduler` 里那句立刻执行的 `tick()`）就会把它补发出去。回归用例因此多钉一条：锁还锁着时，行必须仍是 `pending`。

**把认领往后挪只是把窗口缩小，没有消除它**（自动验证第 1 轮指出，同日补完）：`claim` 仍是「`pending → sent` 之后才去送」，进程死在这两步之间，留下的就是一条谁也捞不回来的 `sent` 行——补发扫描只查 `pending`。根治要把「有人正在送」和「已经送到」**拆成两个字段**：新增 `scheduled_messages.delivering_since` 当投递租约，行本身**始终留在 `pending`**（托盘照常显示「待发送」，这也是诚实的：它确实还没发出去）；`sent` 只由 `continueTask` 的新回调 `onDelivered` 写，那一刻原话刚作为一个真人回合写进会话落盘文件、agent 进程也已经带着它起来了。回调是必要的——`continueTask` 要等**整轮跑完**才 resolve，拿它的返回值标 sent，托盘会在 agent 干活的整段时间里一直显示「待发送」。租约不需要超时启发式：它是内存态的持久投影，进程一换，上一轮所有「正在送」的回调按定义都不存在了，所以 `startScheduler` 开机第一件事就是 `reclaimStaleDeliveries()` 全清、再跑第一次 tick。**代价方向是刻意选的**：万一死在「原话已落盘、`sent` 还没写」的毫秒缝里，结果是重发一次，而不是丢一句话。

顺带纠正一个测试反模式：原来「排队追问」那条用例先等 `status === "sent"`、再等会话行出现。这个顺序本身就默认了「sent 可以先于原话落盘」——在负载高的机器上它会真的先到，用例随之偶发变红（第 1 轮验证报的就是它）。断言顺序要跟不变量同向：**先等会话真的起来，再看状态位**。另外 `waitFor` 的 3 秒上限也太紧了，每一步都在真起进程、真写盘，超时是用来兜死锁的，不是用来卡性能的，已放宽到 15 秒。

崩溃这一格没法在同一个进程里装出来，所以回归用例**真的 fork 一个进程**：子进程用投递路径自己那个 `beginDelivery` 抢下租约，然后 `SIGKILL` 自己（没有 finally、没有清理），父进程随后断言库里留下的是「`pending` + 有租约」，且这时谁都不许插手投递（否则同一条会发两遍），最后走真实开机路径 `startScheduler()` 确认它被补发进会话。把开机那句回收删掉、或把 `beginDelivery` 改回旧的「顺手标 sent」，这条用例都当场变红。

一条可迁移的推论：**「消息/指令类的东西被标成已处理」和「它真的被处理了」必须是同一件事**，中间隔着一个静默 return 就是一次数据丢失。凡是先改状态再触发副作用的地方，都要问一句「副作用没发生的话，这条状态谁来退回去」——而「退回去」只在进程还活着时才算数，所以更硬的版本是：**别先改状态**，把「正在处理」写成一个独立的、开机能回收的标记，终态只在副作用**落盘之后**才写。
