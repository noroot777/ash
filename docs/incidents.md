# 事故档案

这里存的是根 `CLAUDE.md` 里那些约定的**来由**：踩过的坑、实测复现出来的现象、试过且被证伪的路。

分工是明确的——**规则本体留在 `CLAUDE.md`**（那是每次动手前都要读一遍的东西），**事故经过放这里**（那是想知道「为什么非得这么写」「这条能不能改」时才翻的）。

搬迁原则：**整段原文迁移，不压缩、不改写**。这些踩坑记录是这个仓库最贵的资产，压缩掉的一定是「为什么」，而那正是唯一不可再生的部分。

## 僵尸调度器：明明确认了却记 failed（2026-07-27）

对应约定：`CLAUDE.md` 的「完成确认**同时落库**」。

一个没监听但调度器还活着的僵尸实例在跑任务，agent 的 `complete_task` 落进了监听进程的内存 Set，结算那边什么都没看见 → 明明确认了却记 failed，队列跟着停摆。

## 停止全组：后端全做对了，用户却只能得出「按钮坏了」（2026-07-27）

对应约定：`CLAUDE.md` 的「停止/暂停类操作必须在 UI 上留下持久可见的状态」。

点「停止全组」后端全做对了——进程 SIGTERM、内部组置 `paused`、会话写入系统提示——但按钮原样、状态徽标不动、`paused` 前端压根没渲染，用户只能得出「按钮坏了」。

更坏的是它**掩盖了真问题**：界面若明说「已停止，0 个执行者被打断（都已完成）」，用户立刻就知道还在动的鼠标不归 harness 管，而不是把一个架构缺口误报成 UI bug。

## CUA 旁路会话：harness 够不着的全局单例（2026-07-27）

对应约定：`CLAUDE.md` 的「三层击杀只覆盖 harness 自己 spawn 的进程树」。

codex 的 computer use 由 `/Applications/ChatGPT.app` 侧拉起 `SkyComputerUseService`（**开机级全局单例**，跟着宿主 App 一起启动，不是每任务一个），harness 的进程组/fd/ppid 三条线索一条都够不着它。

**已验证有效的手段**：`stopTask` 三层击杀掉执行者后，`SkyComputerUseService` 随即消失，屏幕指示器跟着走（CUA 服务有 `shouldTerminateWhenNoClientsRemain` 语义，codex 客户端一死它就自行退出）。

**已被实测证伪、别再试的路**：`SkyComputerUseClient turn-ended`。在**活跃** CUA 会话上手动调过 4 种 payload（`thread_id` 用真实 `cliSessionId`、加空 `turn_id`、`codex.app_session_id`、`threadID`），**全部 `exit 0` 且毫无效果**，服务照活、执行者照常截图；那个 CLI 对任何输入（包括非 JSON）都静默返回 0，「成功」是假象。

**仍未验证的一条**：agent **正常完成**（而非被杀）时服务会不会残留——两次对照实验都因 codex 选择用 Orca 截屏而没能触发 CUA，**别把「没验到」说成「不会发生」**。

**清理盲区**：`pauseGroup` 只处理 `running`/`queued` 成员，已 `done` 执行者遗留的旁路会话没人管——2026-07-27 用户点「停止全组」时执行者早已全部 done，鼠标却还在屏幕上动。

## 端口撞车产幽灵：不占端口、但调度器在轮询生产库（2026-07-27）

对应约定：`CLAUDE.md` 的「启动期的致命错误必须 `exit(1)`」「同一个数据库文件同一时刻只允许一个 server」。

单实例守卫只挡「同一个 DB」，**端口撞车是另一条产幽灵的路**：`PORT=4317 HARNESS_DB=/tmp/x.db` 能顺利拿到 DB 锁，然后在 listen 那步撞死；旧代码里 scheduler 已经先起来了，EADDRINUSE 又被通用兜底接住只打日志不退出，于是留下「没有端口、但调度器在轮询生产 DB」的活死人。

实测复现：修复前第二个实例在 EADDRINUSE 后照样存活并 `scheduler started`；修复后 exit 1、日志里 `scheduler started` 出现 0 次。

而「不同 DB 并存」是既定的 throwaway 验证工作流，不能靠收紧锁粒度来解决。

同源的另一个现象：第二个实例**不占端口所以 `lsof` 查不出来**——2026-07-27 实测发现一个 7 月 22 日起的幽灵实例活了 5 天没人发现。

## 没有监听者的 `'error'` 把任务永久卡在 running（2026-07-28）

对应约定：`CLAUDE.md` 的「预检失败的 `'error'` 事件不能立刻 emit」。

抢在订阅者挂上之前 emit `'error'`，EventEmitter 直接升级成 uncaughtException，被运行期兜底一吞，run loop 就永远等不到 `done`：**任务卡死在 running、`stopTask` 返回 true 却停不掉、再发消息被 409 挡回，只有重启才能解**。

复现方式：在一个 worktree 已被删除的任务里回复即可。

## 对称端点只改了一个：可点的候选卡片压根没机会渲染（2026-07-27）

对应约定：`CLAUDE.md` 的「凡是对 `tasks.status` 做校验的地方，都要先问一句『这条对常驻调度台适用吗』」。

`/answer` 想到了调度台、`/ask` 没有，于是调度者带 4 个候选选项提问被 409 拒，**网页上那张可点的候选卡片压根没机会渲染**，用户看到的现象是「这个功能你没做吧」。

同一个文件里两个对称端点只改了一个，这类漏点靠通读发现不了，只能靠「改一处就 grep 一遍所有 status 校验点」。

## 只改数据库不停进程的三连错（2026-07-21）

对应约定：`CLAUDE.md` 的「取消/打断任务的唯一正道是 `stop_task`」。

对 running/queued 任务 PATCH status 只改数据库不停进程，会三连错：canceled 提前推进队列（串行变并行）、活着的 agent 调 `complete_task` 吃 409、结算把 canceled 覆盖成 failed。

详见 codex 线程 `019f8d03`。也因此失败告警文案不指控「agent 未调用」——确认也可能是被 409 拒掉的。

## 并行验收互相拆台：同一个工作区两个 merge

对应约定：`CLAUDE.md` 的「同一仓库的写型 git 操作全局串行」。

一个仓库的 `.git` 是所有 worktree 共用的单一状态机，并行写有三种拆台方式：

1. 并行验收里 A 读到 target=X 决定 FF、B 抢先把 target 推到 Y，A 就报 `fast_forward_failed`；
2. 目标分支恰好检出在项目目录时（最常见的 `main`）FF 走不通会退化成**在项目工作区里 `git merge`**，两个验收同时进到这一步 = 同一个工作区两个 merge，实测直接 `Unable to create '.git/index.lock': File exists`；
3. 更坏的情况是 B 失败后的 `merge --abort` 把 A 已完成的合并回滚掉。

## CLAUDE.md 自己的膨胀史（2026-07-29）

对应约定：`CLAUDE.md` 顶部的「新约定按升级顺序找地方放」，以及 `.githooks/pre-commit` 的体积闸。

逐提交量出来的曲线：

```
2026-07-27  14,020 字节
2026-07-28  24,122 → 34,720
2026-07-29  35,409 → 41,142
```

三天 ×2.9，日均 +9k 字节 ≈ +2.7k token/天，57 次提交里只有 3 次是净减少（还都是删功能带的）。

三笔额外的账：

- **token 税**：41,142 字节 ≈ 12.5k token，每个 claude 执行器每轮都付。
- **冲突热区**：一个全局单点、append-only、没有天然分片的 40+ 项列表，配上 N 个并行 worktree agent，冲突是必然的——某次验收循环里撞了 3 次合并冲突，冲突文件**全部只有 CLAUDE.md**，代码文件零冲突。
- **对 codex 从来没生效过**：codex 读的是 `AGENTS.md`，而根目录没有这个文件。`mobile/` 里两份都有（`mobile/AGENTS.md` 是正文，`mobile/CLAUDE.md` 只有一行 `@AGENTS.md` 指过去）——这个仓库自己已经解过这道题了，根目录漏了。而系统并没有因此崩掉，这反过来证明真正在约束 agent 的是做进系统的那部分：`complete_task` 的 prompt 前言注入、running 状态 PATCH 的 409 硬拦、`resolveExecutorFor` 的 API 形状。

根因不是「攒多了该清一次」，是**成本外部化**：加一条 CLAUDE.md 成本 2 分钟、当场生效、写进交付总结还显得周到，收益全归本轮 agent；而账单落在下一个 agent 的入场费和下一次并行冲突上，那时加条目的 agent 早已验收走人。原元规则只说「值得就主动补一条」，全文没有任何一句奖励「搬走一条」或「做进系统」。

所以修的是激励而不是劝自觉：把账单送回产生成本的那一刻（commit），并让「减」和「加」一样可见。

## 关口画在验证前面就被跳过（2026-08-05）

对应约定：`server/CLAUDE.md` 的「执行者彻底退出自我验证 / 就地验证」一条，以及推进器文件头（`server/src/workflow-advance.ts`）那三条不变量。回归：`npm -w server run test:workflow-gate`、`npm -w web-next run test:workflow-rail`。

用户的原话是「等我点头这一步都没等我去打开预览瞅一眼，点个确认或补充点信息，就自动开始第四步的自动验证了」。任务 `bq3PLDuZzZOt` 的线是 **干活 → 打开预览 → 等我点头 → 自动验证 → 合并并清理**，关口画在验证**前面**。执行记录里的证据链：

```
06:29:46.311  预览已起
06:29:46.317  stage=verifying          ← 关口零停留，相差 6 毫秒
06:56:48      时间线原话：「这条线上没写「等我点头」，走到「合并并清理」就自己合了。」
```

`tasks.workflow_at` 全程为 **null**，而线上明明画着 human 站——最后那句时间线是这次事故最有价值的一行：系统不是「忘了停」，是**真心认为这条线没写关口**。

根因有两层，都在「按锚点类型读线」这个旧模型里：

1. 旧推进器按锚点**类型**决定下一步，顺序写死成「验证 → 关口 → 合并」，用户画的顺序根本没人读；
2. `workflowPolicy.humanGate` 当时的判据是「有 human 站**且排在 verify 之后**」，于是关口画在前面时整条线被判成「没写等我点头」，一路自动验证 + 自动合并到底。

第二期把段落切分改成按**站 id** 走（游标 `tasks.workflow_at`）之后，服务端这条路已经修好；但同一次排查里发现另外三处仍活着的同类错误，它们跟 dist 新旧无关：

- **前端游标没跟着换**（`web-next/src/workflow/workflowModel.ts`）：文件头当时写着「第二期落了真游标就换掉这里」，游标落了、这里没换，仍从 stage 反推。`stage=verifying` 时反推指向 verify 站，排在它前面的 human 站于是被画成「✓ 已过」——用户看到的是「我压根没点头，它却说我点过了」。
- **关口按钮只看 stage**（`WorkflowInspector.tsx` 的 `atHumanGate`）：`awaiting_acceptance` 只说明有人把任务标成了待验收，可能是 agent 按完成协议自报的，也可能属于线上**另一道**关口。照它给按钮，用户会在一道还没轮到的关口上按下不可逆的验收。
- **关口静默停下**（`server/src/review.ts` 的 `enterHumanGate`）：stage 已是 `awaiting_acceptance`（agent 自报）时整个函数直接 return，那句「这条线走到「等我点头」」的时间线一个字都不写。任务停着不动，用户无从判断它是在等自己点头还是卡住了——这正是「停止/暂停必须留下持久可见的状态」那条规则的同一种病。

三条推论：

- **「线上有没有这一站」和「此刻停在哪一站」是两个问题**，前者读定义、后者读游标，任何一处拿 stage 当站的代名词都会重犯这次的错。
- 用户能把站排成任意顺序，就不能有任何一处代码假设某种顺序；`SINGLETON_KINDS` 那种「同类站只能有一个」的限制也是同一个假设的产物。
- 这次真正的证据不是那张截图，是执行记录里 6 毫秒的间隔和那句「这条线上没写等我点头」。**用户报「流程没走对」时，先去翻那条任务的时间线**，比读代码推断快一个量级。
