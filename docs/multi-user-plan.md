# ash 多用户机制设计(定稿)

状态:定稿于 2026-08-27,经五轮逐分支讨论拍板(任务 dsZcltM6cTHe)。本文是唯一完整方案,
**不分 v1/v2**——所有语义一次定死;文末「实施顺序」只是开发排期建议,不是功能分版。

## 一、定位与信任边界

多人模式定位为**相互信任的小团队协作**:解决防误操作、各人各视图、数据归属清晰。
**不解决防恶意用户**——所有 agent 与 server 以同一个 OS 用户运行,目录/项目权限是
API + UI 层的护栏,不是 OS 级隔离;恶意用户可以让自己的 agent 读写任意路径,系统拦不住。
真正的 OS 级隔离(容器/多账户)不在本方案范围。

随之而来的「机器共享现实」清单(全员共享、没法按 ash 用户分,如实写给用户看):

- **CLI 登录凭证与订阅额度**:执行器不挂供应商时用宿主机 CLI 自己的登录(`~/.claude` 等),
  所有用户烧同一份订阅,无法分账;挂了供应商(自带 API key)的执行器才能按人分。
- **宿主级 skill 与插件**:`~/.claude/skills`、`~/.claude/plugins`、`~/.codex/skills` 等
  是 OS 用户目录里的东西,整台机器一份。私有 skill 的正道是放进自己项目仓库的
  `.claude/skills`(项目级来源天然跟项目权限走,见 `server/src/skills.ts`)。
  「每 ash 用户注入独立 CLAUDE_CONFIG_DIR/CODEX_HOME」的深隔离路线已评估、**不采用**:
  它连 CLI 登录一起隔开,每人得自己登录或自带 key,运维重且脆。
- 传输安全靠 Tailscale/反代 TLS,系统本身不做 HTTPS(与现状一致)。

## 二、实例模式:自用 / 多人

- 实例级设置 `instanceMode: "single" | "multi"`。
- **首启向导**:模式未定时首次访问进向导页。选「自用」→ 直接进,保持现状零鉴权;
  选「多人」→ 填管理员姓名 + 根目录路径 → 生成管理员 key 整屏展示一次,强制点
  「我已保存」→ 进登录页。
- **自用 → 多人**:设置页危险区提供转换,流程同上(姓名 + 根目录必填)。
- **多人 → 自用:永不提供**,界面写明原因(多人数据无法合并回单人)。
- 鉴权中间件只在 multi 模式生效;自用模式一行不拦,现有单机用户零感知。

## 三、身份与认证

- **无注册模块,key 即身份**。`users` 表:姓名、实例角色(admin/member)、目录名、
  keyHash、状态(invited/active/suspended)、创建人、最近活跃。
- key 形如 `ash_` + 高熵随机串;**库里只存哈希**,仅在领取/重生成时整屏展示一次。
- **web 登录**:粘贴 key → 换 HttpOnly cookie 会话(服务端会话表,30 天滑动过期);
  SSE(`/api/events`)天然复用 cookie。登出=删会话。
- **mobile**:设置页在「后端地址」旁增加 key 字段,每请求带 `Authorization: Bearer`。
- **agent/MCP 流量**:agent 回连 server 已带回合凭证(`x-ash-turn-token`,
  `mcp/src/index.ts`),中间件按「有效回合凭证 → 任务归属项目」放行,不走用户会话。
- **key 轮换**:用户在个人设置里可自助重新生成(旧 key 即刻失效,新 key 展示一次);
  管理员也可为任何用户重置(生成新的专属邀请链接让他重领)。
- **逃生门**:唯一管理员丢 key 时,在宿主机跑 CLI 命令(能碰到数据库文件的人本来就
  拥有一切)生成一条新的管理员邀请链接;不破坏「无注册、凭 key 登录」模型。
- 中间件豁口:`/api/health`(重启脚本与手机探针)、`/api/handoff/*`(自有 ed25519
  签名体系,用户级校验见第十节)、登录页与 claim 页本身。

## 四、角色与权限

**实例级两档**:管理员 / 普通用户。管理员与初始管理员同权。
**项目级两档**:项目管理员 / 项目成员。创建者自动成为项目管理员。

| 能力 | 普通成员 | 项目管理员 | 实例管理员 |
|---|---|---|---|
| 登录、个人设置、配置导出导入 | ✓ | ✓ | ✓ |
| 在本人目录内建项目/克隆 | ✓ | ✓ | ✓(不限目录) |
| 可见项目内:派任务/回复/打回/**验收** | ✓ | ✓ | ✓ |
| 项目成员管理(邀请/移除/改角色) | — | ✓ | ✓ |
| 项目设置(改路径/归档/删除) | — | ✓ | ✓ |
| 用户管理、根目录、实例设置 | — | — | ✓ |
| 项目终端(宿主机 shell) | — | — | ✓(仅管理员,前端隐藏+后端 403) |
| 全部项目可见/可进 | — | — | ✓ |

- 验收(accept_task 合并主干)是工作流闭环动作不是管理动作,普通成员可做。
- 实例管理员进任意项目时权限等同项目管理员。
- 用户名单(姓名+角色)对全员可见——项目管理员邀人时要选人。
- 分组/日程等跟项目走:项目可见即可见。

## 五、用户管理(实例层,仅管理员)

设置页新增「用户」节:

- 列表:姓名 / 目录名 / 角色 / 状态 / 最近活跃。
- **添加用户**:填姓名 + 目录名 + 角色(普通用户/管理员)→ 在根目录下创建其目录 →
  生成**专属邀请链接**(一人一链)。实例开户**只有这一条路**,没有自助注册。
- **专属邀请链接**:7 天未领取自动过期,管理员可随时作废/重发。领取流程:打开链接
  先看到说明页 → 点「领取」才生成并展示 key(停留期间可复制)→ 点「我已保存」后
  链接作废、账号转 active。避免「手滑点开没保存就作废」的锁死。
- **停用/恢复**:停用立即断该用户所有会话;不做删除(牵扯归属转移,只停用)。
- **重置 key**:走专属邀请链接重领,旧 key 即刻失效。

## 六、项目成员与邀请(项目层)

- **只能邀请实例中已存在的用户**;不在系统里的人,提示「找管理员开通账号」。
- 两种邀法并存,均无「接受」步骤(直接加入 + 站内通知):
  1. **选人直加**:项目管理员从实例用户名单选人,立即加入,指定角色。
  2. **项目邀请链接**:一条链接发群里,多个已有账号的用户点开即加入该项目。
     已登录直接进;未登录先输 key;无账号提示找管理员。链接只能发普通成员角色,
     可作废/设有效期。
- 项目管理员可移除成员、改角色;成员可自行退出。

## 七、目录模型

- 实例设置 **根目录 rootDir**(仅管理员,转多人时必填);每个用户在其下有一个目录
  `rootDir/<dirName>`(添加用户时创建,目录名做 slug 校验)。
- **普通用户**的项目路径钳死在本人目录内:新建项目可**选择本人目录内已存在的子目录**
  (不必每次新建目录)、也可新建目录、或克隆(目标限本人目录内)。
  服务端用 realpath + isInsidePath 钳制(复用 `server/src/file-browser.ts` 的防软链
  越狱原语)。
- 「浏览」改为**网页目录树选择器**(新做受限 fs-browse API,根钉死在本人目录);
  现有的原生桌面弹窗(`dir-picker`)对普通用户停用——它弹在服务器桌面上,对远程
  用户无意义。
- **实例管理员豁免**:可在任意路径建项目,保留原生弹窗与手输路径。
- 存量项目(转换前创建的)路径一律不动。

## 八、数据归属:全部按人隔离

按用户的原则「系统设置里的功能仅对此人可见/生效」,资源一律按人:

- **个人面(每人自己的,互不可见)**:供应商(**不做共享池**,每人自带 API key)、
  执行器、执行模式、起手式、审查者、团队预设等资源条目;默认规则(worktree 默认、
  默认起手式);随手记(转私有);我的 key。
- **实例面(仅管理员)**:用户管理、根目录、实例模式、技能扫描间隔(机器级轮询行为)。
- 新成员冷启动靠**配置导出/导入**(第九节),不靠共享库。
- 实现注:上述资源表逐一挂 `userId`;任务/会话/分组跟项目走,不挂个人。

## 九、配置导出 / 导入

- 导出为 JSON 文件,内容可勾选:执行器 / 执行模式 / 起手式 / 审查者 / 供应商。
- **API key 一律不随文件走**:供应商条目只导结构(名字/base_url/型号),导入后自己填
  ——导出文件会在聊天工具里传,带 key 就是泄露渠道。
- 这份文件同时是管理员给新成员的「起步包」:建完账号把自己的配置导出发给他导入。

## 十、接力(跨机,统一设计,全员可用)

原则:接力不是管理员专属,所有用户都要用;同时**对端项目列表不得向发起人暴露其无权
看到的项目**。两条要求合起来推出:

- **跨机身份 = 你在对端机器上的账号 key**。与项目邀请同一哲学:要在那台机器上做事,
  就得在那台机器上有账号(找那台机器的管理员开)。不做隐式的跨机用户映射。
- **目标机器配置按人**:每个用户配自己的目标机列表 `{名称, url, 机器指纹, 我在对端的
  key}`。对端 key 是凭证,存储同 `project_git_credentials` 待遇——落库不回显。
- 机器级 ed25519 签名保留,降级为**传输信任**(哪台机器可以连我);其上叠加用户级
  授权(这台机器上的哪个人在请求)。
- **对端为多人模式**:ping/preflight/import 全链路携带发起人的对端 key;对端校验后,
  项目列表按**该用户在对端的可见集**过滤;导入要求该用户对目标项目有权限;落地任务
  记录创建者为该对端用户。key 缺失/无效 → 明确报错,UI 提示「在对端机器上没有账号,
  找对端管理员开通」。
- **对端为自用模式**:忽略用户 key,行为与现状一致(机器级信任即全部)。
- **本机为自用模式**:目标机配置仍在实例设置(现状),按需增填「对端账号 key」字段。
- **来源审批(inbound)**:实例级状态,但**全员可见可批**(互信定位),记录操作人;
  不是管理员专属。
- 发起接力只能从自己有权限的项目发起。

## 十一、可见性过滤(横切面)

多人模式下,以下所有面都按「本人可见项目集合」过滤,**以 `/api/events`(全局 SSE,
`server/src/routes.ts:582`)为验收基准——它目前对所有连接者广播一切,最容易漏**:

项目切换器 / 任务列表 / 搜索与命令面板 / SSE 事件流 / 通知 / 统一验收页 / 随手记(私有)。

## 十二、存量数据与转换

自用转多人时:存量项目、随手记、供应商、执行器等资源条目**全部归初始管理员**;
项目路径一律不动(不往根目录搬,不动磁盘上的仓库)。转换完成后刷新即要求登录。
实现建议:自用模式内部也用一个隐式本地用户持有归属列,转换时把它实名化为初始管理员,
避免两套归属逻辑。

## 十三、实施顺序(仅开发排期,不是功能分版)

1. 认证骨架:users/会话/中间件/登录页/首启向导/模式转换/宿主机逃生门。
2. 用户管理 UI + 专属邀请 claim 流程 + 停用/重置/自助轮换。
3. 目录模型:rootDir、用户目录、fs-browse API + 网页目录树、创建/克隆钳制、
   dir-picker 与终端的角色门禁。
4. 项目成员(两种邀法)+ 全面可见性过滤(含 SSE)。
5. 资源表按人拆分(逐表挂 userId)+ 配置导出导入。
6. 接力用户级授权(对端 key 链路)+ 目标机配置按人 + mobile 登录字段。
