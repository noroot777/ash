# 改名 navi ⑤：批量改名脚本与交接

产品从 ash 改名 navi。第 ③④ 步把跨边界的约定（环境变量、分支前缀、库文件、锁、MCP 登记名……）集中定义好，
旧名登记在 `shared/src/legacy-names.ts` 和它的镜像 `scripts/legacy-names.mjs`；第 ⑤ 步用一个可重放的脚本，把
仓库里剩下的、不跨边界的 ash 机械地换成 navi。本文件交代脚本怎么用、剩下的 ash 在哪、合并之后要做什么、
在途分支怎么跟上。

## 脚本由什么组成

| 文件 | 管什么 |
| --- | --- |
| `scripts/rename-navi.mjs` | 入口。按词元认 ash（`hash`、`bash`、`dashboard` 不算；驼峰 `isAshMcp`、下划线 `ASH_DB`、连字符 `ash-presence` 切开后整段是 ash 才算），大小写跟着原词走：ash → navi、Ash → Navi、ASH → NAVI。兼容值按规则跳过。 |
| `scripts/rename-navi-fixes.mjs` | 手写修复层：机械换不出来、交付又离不开的几处（mac 应用与发版脚本读环境变量新旧两代都认、win-remote 按目录名认对端本仓库、被改名带坏的测试夹具等）。同一次运行里在机械改名之后套上。 |
| `scripts/rename-navi-fs.mjs` | 仓库边界：路径上每一级都不许是符号链接，规划时认一遍，动手建目录、挪、写之前再认一遍。 |
| `scripts/rename-navi-report.mjs` | `--report` 的排版，和其中更早一代 harness 那一节的分类规则。 |
| `scripts/test-rename-navi.mjs` | 脚本自己的回归（挂在 `npm run test:accept-scripts` 里）。 |
| `docs/rename-navi-remaining.md` | 交付时那一刻的剩余清单（`--report` 的输出）。 |
| `docs/rename-navi-windows.md` | Windows 真机验证（第 ⑦ 步）的记录和那台机器的升级操作单。 |

这几份整份不进改名：里面的旧名是规则和说明本身；Windows 那份写的是改名前那台机器上的事实（`ASH_*` 变量、`ash/` 分支、旧锁文件名），换了就写错了。

## 用法

```sh
node scripts/rename-navi.mjs            # 在当前检出上改；要求工作区干净（没加进 git 的文件也不许有）；不提交，看过再自己提交
node scripts/rename-navi.mjs --dirty    # 有未提交改动、没加进 git 的文件也照跑（失败时不能靠整仓重置回退）
node scripts/rename-navi.mjs --check    # 只看不改：还有要改的（机械改名或手写修复）就列出来、退出码 1
node scripts/rename-navi.mjs --report   # 打出剩下的每一处 ash 与理由，harness 那一代单列
```

退出码：

- `0`：做完了（`--check` 时表示没有要改的）。
- `1`：`--check` 发现还有要改的。
- `2`：没动手就拒绝了。有三种可能：
  - 工作区不干净（没加 `--dirty`）。
  - 挪名的落点已经有文件。
  - 有做不完整的文件：还没提交的删除；要挪名、链接里写着旧名的符号链接；路径上有目录链接的文件或落点；
    索引项有没解决的冲突、或带着 intent-to-add / assume-unchanged / skip-worktree 标志的；不是合法 UTF-8、里面又写着旧名的
    （见下面「正文怎么认」）。`--check` 碰上这种也返回 2，不算通过。
- `3`：改到一半失败。会列出已经做完的步骤，并给出恢复办法。
- `4`：有文件读不到（权限、IO），没法判断要不要换。
- `5`：手写修复对不上（原文找不到，或要新建的文件那里已经有一份别的内容），一个文件都没动。

脚本过一遍的文件是「已跟踪的 + 没加进 git、也没被 .gitignore 忽略的」，改名、`--check`、`--report` 用的是同一份：
分支上刚写、还没 `git add` 的新文件照样改名、照样被核对。不加 `--dirty` 时有这种文件就拒绝（返回 2），因为它们改坏了
`git reset --hard` 退不回来。

正文怎么认（文件名一律照常挪，这里只说正文）：

- 扩展名在脚本的 `BINARY` 名单里的（图片、字体、压缩包、库文件……）：二进制格式，正文不看。字节里出现了 ash 的，`--report` 的 `not-text` 一节点名。
- 其余的按 UTF-8 解码再编码回去，逐字节一样就是文本，照常改名，没换的字节原样写回。**含 NUL 字节的也算**：NUL 在 UTF-8 里是合法字符，
  源码里拿它当分隔符的照样是文本（`server/src/handoff-capability.ts` 曾因为含 NUL 被当成二进制整份跳过，核对和清单都不报）。
  这种文件 `--check` 和改名的输出里会标「含 NUL 字节」，`--report` 的 `nul-text` 一节逐个列出。
- 逐字节对不上的（GBK、Latin-1 之类别的编码，或没登记扩展名的二进制）：解码时坏字节会被换掉，写回去就毁了，所以不改。
  里面写着 ash 的整次拒绝（返回 2），`--report` 的 `not-text` 一节也列着。是别的编码的文本就手工改；是二进制就把扩展名加进 `BINARY`。

正文只读写仓库里的普通文件，而且路径从仓库根往下每一级都不许是符号链接：文件本身是链接、所在目录是链接、
挪名的落点在链接下面都算。碰上这些，链到仓库外的东西一样都不会被读、被改、被建出目录来。
要挪名的链接、链接里写着旧名的、在目录链接下面的文件，脚本整次拒绝，让你手工处理。
还没提交的删除（索引里有、工作区里删掉了）要挪名或要套修复时，同样在动手之前整次拒绝，不会挪到一半才发现源文件不在。

这条边界在规划时认一遍。动手时每一步再认一遍，源和落点都要认：
- 挪之前，源路径上每一级仍不是链接，源仍是规划时那一份文件（同一个 inode）。
- 改正文时，落点仍是规划时那一份，内容也没被改过（动手前核一次，换上之前再核一次，见下面）。

规划之后被别的进程换掉、改掉的，脚本在那一步停下，返回 3 并列出已经做完的步骤，不拿规划时的结论去挪、去盖。
按路径改磁盘的系统调用一共这几处：建目录、建临时文件、换上正文（改名）或新建（硬链接）、挪名、删临时文件。
每一处都照同一个次序：
- 慢的先做：读原文、写临时文件、建落点目录。
- 最后只做便宜的核对：逐级 lstat，按 lstat 比身份和戳（inode、大小、纳秒的内容改动时间和 inode 改动时间）。
- 核完紧接着就是那一次系统调用，中间不夹读盘、建目录、起进程。

往临时文件里写、改权限位、落盘走的是建它时拿到的句柄，写的是自己刚建的那个文件。删临时文件时，所在目录已经被换成链接、
或者那个名字已经不是自己建的那个文件，就不删，记进失败清单让你手工删。

已跟踪文件的挪名不用 `git mv`，因为它另起一个进程去挪，核对贴不到它那次改名前面。脚本改成自己改名，再把索引项
（文件模式和暂存的那份内容）原样挪到新名上，暂存的内容不变。
- 索引在规划时整份读一次，按路径逐字认。不拿路径去问 git：git 把路径参数当通配模式，`ash[1].txt` 会配上 `ash1.txt` 那一项。
- 脚本只替普通的索引项挪名、改正文。有没解决的冲突的、带 intent-to-add / assume-unchanged / skip-worktree 标志的，
  在规划时整次拒绝，并告诉你先做什么（解决冲突；`git add`；`git update-index --no-assume-unchanged`、`--no-skip-worktree`）。
  原因：这些标志挪名带不走，后两种还会让 git 看不见正文的改动。
- 更新索引失败时，git 不会换上新索引，索引里还是旧名那一项。失败清单里给出把文件挪回去的命令，路径已经加好引号。

最后那次核对和紧接着的那一次系统调用之间的瞬间不防。所以别在别的程序同时改这个工作区的时候跑。

改正文的写法：
- 新正文先完整写进同一目录下的临时文件，写满并落盘，再一步换上：改已有的用原子改名，权限位照旧；新建的用硬链接，落点有东西就失败。
- 换上之前的最后一刻再核一遍：所在目录每一级不是链接，落点仍是规划时那一份、内容没被改过（新建的落点仍空着）。
  写临时文件期间别的程序保存了、原子保存换了文件、把目录换成了链接，都在这里拦下：丢掉临时结果，停下。
- 写到一半失败（磁盘满、IO 错），或者换上之前发现变了，只删临时文件，原文件一个字节都不动。
- 换上的那一刻就记进失败清单。之后清临时文件出错，这次改动和留下的临时文件也都在清单里。所以「其余没动」是真的。
- 临时文件名固定且短，不抄原文件名：接近文件名长度上限的文件也改得了。

脚本幂等：换完的地方不再含要换的词；手写修复每一份都带记号，文件里已经有记号就不再碰。所以对已经改完的检出，
再跑一遍什么都不改，`--check` 是 0。

## 在最新的 main 上重新生成

main 每天在动，这条改动和几乎所有分支冲突。验收前不手解冲突，直接在最新 main 上重新生成：

1. 从最新 main 开一个干净的检出（或分支）。
2. 把脚本那一笔提交摘过来：`git cherry-pick <脚本提交>`。这一笔只含上表的脚本、回归和本文件（剩余清单在第 4 步生成）。
3. `node scripts/rename-navi.mjs`。返回 5 时按提示处理：多半是修复层改到的那几个文件在 main 上又被改过，
   手工把对应修复补上（补完文件里就有记号了），再跑。
4. `node scripts/rename-navi.mjs --report > docs/rename-navi-remaining.md`，刷新剩余清单。
5. 根目录和 `mobile/` 各跑一次 `npm install`（工作区包的作用域从 `@ash/*` 换成了 `@navi/*`）。
6. `node scripts/rename-navi.mjs --check` 应为 0，然后把结果提交成一笔。

## 剩下的 ash 在哪

见 `docs/rename-navi-remaining.md`，按留下的理由分组，每组开头一句话说为什么留，下面逐行列出位置。
最多的几组：

- 库文件名 `ash.db`：新老安装、mac 应用都还认这个名字。
- 整份讲兼容的文件：迁移表、兼容回归。
- 旧名登记处：两份清单本身。
- 改名前的 mac 应用：`Ash.app`、`dev.ash.mac`，新版第一次打开时按这些名字接班。
- 同一行写着两代名字：在逐代列举或比对。

第二部分单列更早一代 harness，同样逐行写明理由。其中 `older-prose` 那一组不是兼容值：那是上一次改名
（harness → ash）没换掉的叙述、示例和临时目录名。本次只换 ash，它们原样留着。

## 合进 main 之后，在主仓要做的事

改名动到的、本机正在用的东西一共这几样，用到哪样就做哪样：

1. **依赖链接**：根目录 `npm install`，把 `node_modules/@ash/*` 的工作区链换成 `@navi/*`（根包名也从 `ash` 换成了 `navi`）。
2. **手机端依赖**：`mobile/` 下也跑一次 `npm install`。真机调试时在 `mobile/` 下用 `npm run start`：它带 `--clear`，
   会顺手清掉 Metro 缓存里 `@ash/*` 的旧解析。
3. **构建产物**：`npm run build` 重建 shared / web / server / mcp。用手机端的桌面预览，另跑 `npm run build:mobile`。
4. **:4317 上的服务**：它跑的是构建产物，第 3 步之后重启一次才换上新代码。
5. **mac 应用**（装着 Ash.app 或 Navi.app 才需要）：
   - 跑 `desktop/macos/build.sh --install`。不带 `--install` 只编出 `desktop/macos/build/Navi.app`，「应用程序」里那份不会变。
     它装进 `/Applications`（不可写就 `~/Applications`），装完自动打开。
   - **装着的是改名前的 Ash.app**：别手动删，也别指望它被覆盖。Navi.app 的包标识是 `dev.navi.mac`，跟 Ash.app 是两个应用，
     装的时候不碰它。Navi 第一次打开时会接班：
     - 先请 Ash.app 退出。它不肯退时，Navi 弹窗让你重试。
     - 把设置和网页数据抄过来，数据根继续用原来那块。
     - 换掉旧的登录项 `dev.ash.server`。
     - 等没有进程在用 Ash.app 了，把它移进废纸篓，原地留一个指向 Navi.app 的软链。CLI 里登记的 MCP 路径照样走得通。
   - **装着的是 Navi.app，而且还有进程在用**：安装会拒绝，并列出是谁在用。按提示处理：
     - 手上没有在跑的任务时，结束 Navi 服务（`server/dist/index.js` 那一行）。
     - Navi MCP 是在跑的 agent 拉起的，等那几个任务这一轮结束。
     - 退出 Navi。

     都停了，再跑一次 `--install`。
6. **按路径调用的脚本**：`scripts/ash-admin.mjs` 改名成了 `scripts/navi-admin.mjs`。别名、定时任务里写死旧路径的要跟着改。
   其余挪了名的都是仓库内部引用（测试、服务端模块），不用管。
7. **环境变量**：`ASH_*` 照样认，新名 `NAVI_*` 优先，不改也能用。要换成新名，就把旧的同时删掉：
   指向数据的那几个（库、数据根、连哪台）两代都设了、值又不一样时，会拒绝启动，不替你挑。
8. **各家 CLI 里的 MCP 登记**（`mcp__ash__…`、codex `[mcp_servers.ash]`）：旧登记名照样认，不用手改。
9. **Windows 那台**（192.168.1.187，`D:\ai_workspace\ash`）：同样要做第 1、3、4 步。真机验证（第 ⑦ 步）的记录和那台机器的升级操作单在 `docs/rename-navi-windows.md`。

## 在途分支怎么跟上

1. 先把最新 main 合进分支。冲突里凡是 ash → navi 改名带来的，取分支自己那一侧（内容以分支为准，名字下一步再换）。
2. 在分支上跑 `node scripts/rename-navi.mjs`。有未提交改动、或者有还没 `git add` 的新文件，就加 `--dirty`
   （或者先提交、先 add，再不加 `--dirty` 跑，失败时能整仓重置）。分支自己新写的 ash 会被换掉，
   带 ash 的新文件会被挪名，加没加进 git 都一样；修复层在合进来的 main 里已经有记号，不会重复套。
3. 返回 2 时按它说的原因处理：
   - 「落点已经有文件」：分支新建的旧名文件和 main 上的新名文件撞了。先手工把两份合成新名那一份，再跑。
   - 「在工作区里删掉了、删除还没提交」：先 `git rm` 那个文件（或者把它恢复），再跑。
   - 「符号链接」：手工挪它、改它，再跑。
4. `npm install`，再跑 `node scripts/rename-navi.mjs --check`，确认是 0（没加进 git 的文件也在核对范围里）。
5. 剩余清单不用刷新：它是交付时的快照，分支上别提交它的变化。
