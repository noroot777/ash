## 任务结算

- 完成协议（**exit 0 ≠ done**，agent 必须调 `complete_task`）的规则本体由 prompt 前言注入，不在文档里复述——**别再往任何 md 里加第四份拷贝**。这里只记实现：结算规则单点在 `settleTaskStatus`（`server/src/orchestrator.ts`），优先级 **续聊回合（`followUpFrom`）** > 手停 canceled > 组暂停 paused > 提问 paused（question）> 检查点 paused（resumePrompt）> exit≠0 failed > 已确认 done > 未确认 failed。注入分两处：prompt 前言（fresh run）/ 消息尾部提醒（reply/resume 回合），taskId 一并告知。逃生口 `HARNESS_LAX_DONE=1` 退回「exit 0 即 done」（接没配 harness MCP 的 agent 时用）。
- 完成确认**同时落库**：`/tasks/:id/complete` 写 `tasks.complete_confirmed_at` 并置内存标记（`confirmDone`），`settleTaskStatus` 两边任一命中即算确认、无条件清库。理由：确认走 HTTP 打到**监听**进程，而跑这个回合的未必是同一个进程（事故见 `docs/incidents.md`「僵尸调度器」）。同一事故的另一半兜底在 `server/src/index.ts`：**listen 失败（EADDRINUSE）必须 `process.exit(1)`**，绝不能被 `uncaughtException` 兜底吞掉后留成「不监听但还在派任务」的僵尸调度器；单实例锁（`acquireDbSingletonLock`）是第一道闸，它是第二道。
- 续聊（follow-up）：任务已经到终态（done/failed/canceled）后用户又发消息，这一轮是**任务之后的对话**，不是任务的执行——`continueTask` 把续聊前的终态记进 `tasks.follow_up_from`（只认真人消息：带 `opts.system` 的 retry/运行/队列推进/唤醒照旧算执行），结算后清空。两条推论：①**队列一律按 `followUpFrom` 看待该成员**（`queueStatus()`，`server/src/scheduler.ts`，`selectNextInQueue` 与 `queueBlockers` 共用）——既不算「有人在跑」冻住整条线，也不会被当可启动项拉起；②**续聊只能让任务变成 done（本回合亲口确认），不会让它变差**——没确认/异常退出/手停/组暂停一律回到原终态，回合里提问也只记 `question` 不改状态。回合尾巴换成 `FOLLOW_UP_REMINDER`（别拿「不确认就 failed」吓唬 agent）。理由：给已完成任务发一句「再发布一下」，既不该冻住后面的流水线，也不该把 done 打成 failed（2026-07-27 事故）。
- `reconcileInterrupted`（重启后收拾 running/queued 残留）**逐个走 `setTaskStatus` 单点**，不用批量 UPDATE：单点才会维护 startedAt/endedAt、广播 `task.status`、并触发 `advanceQueueFromTask`——否则重启把队列 head 打成 failed 后没人推进，整条串行队列一直停着等人手点。被打断的续聊回合回到 `followUpFrom` 那个终态（别把早就完成的任务记成 failed）。
- `tasks.stage` 是与 `TaskStatus` **正交**的展示/协作字段，绝不进入 `selectNextInQueue`、`queueBlockers`、`settleTaskStatus` 等调度结算语义；枚举顺序统一来自 shared 的 `STAGE_ORDER`。**执行者彻底退出自我验证**：普通完成协议不再注入 implemented/verifying/verified/verify_failed 自报，团队执行者亲口 `complete_task` 确认 done 后，若 `review_requested=1`，由 `server/src/review.ts` 单点创建不进 queue 的独立审查任务；审查启动把被审任务置 verifying，审查者真实运行产物（web 必须起服务、浏览器确认并截图）后对被审任务上报 verified/verify_failed。证据固定落 `data/runs/<被审taskId>/review/round-<n>/`，`report.md` 必写。第一轮失败会把报告和证据路径交回原任务修复，确认完成后自动复审；自动上限两轮，第二轮仍失败停等人，手动派审可继续追加轮次。审查创建/结束走 `task.review` SSE，stage 变化仍走 `task.stage`；审查编排只挂真实 run loop 结算后的旁路 hook，绝不进入队列推进语义，也不能被续聊回落原终态误触发。
- **已验收任务再被真人唤醒，`stage` 自动清回 `null`**（`reopenAcceptedStage`，`server/src/task-stage.ts`）：`single`/`team`/`debate` 只要 `stage === "accepted"`，`continueTask` 收到**真人消息**（`!opts.system`，与 `followUpFrom` 同一条口径——retry/手点运行/队列推进/上游唤醒不算）就撤销旧验收结论并广播 `task.stage`；团队 `dispatchWorkers` 成功建出执行者时也走同一入口。干完后任务可再次验收。**必须走内部函数而不是 `POST /tasks/:id/stage`**：那道 `mode === "team"` 的 409 挡的是 **agent 自报**的外部协议入口，不该挡内部规则；广播也一步都不能省，否则列表分组与详情按钮要等下次全量拉取才更新。理由：accepted 只代表上一版产物已验收，不能继续覆盖验收后的新增改动。

## 队列

- 队列失败不拖链：head 为 `failed` 时**透明跳过**（同 done/canceled），failed 结算也触发 `advanceQueueFromTask` 推进——失败的任务留在原地等用户重试/处理，后面的照常跑；要「挡住下游等人拍板」用 `awaiting_review`（唯一仍链停的状态）。理由：串行流水线一个环节挂了不该冻结整条线（用户可随时单独重试失败项）。「透明跳过」是同一条规则的两个口径，两处必须一致：自动推进在 `selectNextInQueue`（`server/src/scheduler.ts`），手动点运行在 `queueBlockers`（`server/src/queues.ts`，`/run` 与 `/fire` 共用）——done/canceled/failed 三种都不算挡路。
- **一条 queue 同一时刻至多一个成员在跑**，守卫单点在 `selectNextInQueue`（`server/src/scheduler.ts`）：整体扫一遍，只要有成员 running/queued 就一个都不启动，**不能只靠「顺序扫到才发现」**。理由：被透明跳过的终态任务（典型：failed）一旦回到 backlog，它的位置就排在正在跑的那个**前面**，顺序扫描先命中它就并跑了（实测：05 失败 → 06 起跑 → 05 重新排队 → 两个一起跑）。守卫放在这一层，`advanceQueue` / `runGroup` / queues 的 reorder·remove·insert / requeue 所有入口一起受益。
- 「重新排队」的唯一入口是 `POST /tasks/:id/requeue`（UI 按钮、MCP `requeue_task` 都走它）：一次原子做完「failed/canceled → backlog + 定位置 + 推进队列」。**位置规则**：队列里排在它后面的成员有人已经开跑过（`startedAt` 非空或此刻 running/queued）→ 移到**队尾**（原位置已名存实亡）；没人跑过 → 原位不动（整组还没启动时尊重用户编排的顺序）。判定与重排是纯函数 `isOvertaken` / `tailOrder`（`server/src/queues.ts`，单测在 `server/scripts/test-queue-order.ts`）。理由：前端曾用「PATCH backlog + runGroup」两步拼，中间那一瞬间就是并跑窗口。
- 分组暂停结算 **paused**（不是 canceled）：POST `/groups/:id/pause` 对 running 成员调 `stopTask(id, "paused")`，run loop 结算落 paused；canceled 仅来自用户手停单个任务。理由：canceled 被队列透明跳过，恢复分组会错启下一个；paused 占住 head，恢复（`/groups/:id/run`）时从原 CLI 会话续跑被打断的那个。「组暂停打断」的识别特征是 paused 且无 resumePrompt/question（这是该组合的唯一来源）——parallel 组（无 queue）恢复时 `runParallel` 靠它把被打断任务一并唤醒；debate 任务无 resume 机制，被组暂停杀掉仍落 canceled。

## 进程与启动

- **agent 活得过 server 重启，靠的是「输出走文件而不是匿名管道」**（`server/src/executors/detached.ts`）。根因先记清楚：agent 早就是 `detached: true`（自成进程组），`restart.sh` 那句 `kill` 根本打不到它们；**真正杀死它们的是 stdout 匿名管道**——server 一死读端关闭，agent 下次写 stdout 吃 SIGPIPE 当场毙命。这是唯一的生死绑定，换成文件就断了。五条要点：①一次性 `run()` 走 `spawnForRun(..., opts.detach)`，套一层 shell 把 stdout/stderr 重定向到 `data/runs/<task>/<sess>-<turn>.agent-out.jsonl` 等文件、跑完把退出码写进 `.agent-rc`（管道模式下退出码是 `close` 事件白送的，换文件后没人给）；②`tailFile` **只吐完整的行**，所以 `sessions.agent_offset` 永远落在换行边界，重启后从那里接着读绝不会把一行 stream-json 劈成两半；③合成对象**伪装成 ChildProcess**（同 `failedChild` 的套路），于是所有 parser 一行都不用改；④**常驻会话（团队调度台）不走这条路**——它是双向的，harness 还要往 stdin 塞消息，文件替代不了；它靠 `team/session.ts` 的 `deliver → openLead` 用 `cli_session_id --resume` 自动接回，另有 `wakeInterruptedLeads` 补上「被打断时手头执行者已全部跑完、再没人来唤醒它」的空档；⑤`killByPid` 只剩三层击杀里的第①③层（进程组信号 + 补 SIGKILL），**逮不到重启前就已逃出进程组的孤儿**——那份继承 fd 的映射是内存态的，随旧进程一起没了。回归 `npm -w server run test:detached`（三个真实进程，硬杀中间那个）。
- **`reattachRunningTasks()` 必须排在 `reconcileInterrupted()` 之前**（顺序由 `server/src/index.ts` 保证），这不是风格问题：反过来的话，一个**正在干活**的 agent 会先被判 `failed`，用户一点重试就有第二个 agent 进同一个 worktree 写同一批文件——那是数据损坏，不是显示问题。`reconcileInterrupted` 用 `runs.ts` 的 `isRunning()` 判断谁已被接管（中立模块，依赖保持单向：`reattach.ts → single-run.ts`，orchestrator 不回引 reattach）。接不回来的一律按老语义走：**宁可多判一次中断（用户重试即可），也不能误接一个不是它的进程**——所以 `isSameProcess` 要 pid **和** `ps` 启动时间一起比对，光 `kill(pid,0)` 只能证明「有个进程叫这个号」。回归 `npm -w server run test:reattach`。
- 取消/打断任务的唯一正道是 `stop_task`（POST `/tasks/:id/stop`）：三层击杀（`killChild`，claude/codex 共用）——①进程组信号（spawn 时 detached 成组，kill -pid）；②继承 fd 追踪（spawn 时把本次运行专属追踪文件的 fd 作为 stdio[3] 传入，stop 时 `lsof -t` 反查持有者 + 从持有者向下走 ppid 树补漏）逮住 nohup/自开进程组逃出去的孤儿（真实案例：暂停分组后 TTS 流水线五口之家继续后台跑）；③2s 后统一补 SIGKILL。由 run loop 结算 canceled；queued 没进程的直接落 canceled。**对 running/queued 任务 PATCH status 一律 409 拒绝**——只改数据库不停进程会三连错（见 `docs/incidents.md`「只改数据库不停进程」）。失败告警文案不指控「agent 未调用」，因为确认也可能是被 409 拒掉的。
- **预检失败的 `'error'` 事件不能立刻 emit —— 必须等到有人监听**（`failedChild`，`server/src/executors/spawn.ts`）。执行器返回的 `events` 是**惰性 async generator**（`parseClaudeStream` / `parseCodexStream`），它内部那句 `child.on("error")` 要等 run loop 第一次迭代才挂上，中间隔着好几个 await。抢在那之前 emit = 没有监听者的 `'error'`，EventEmitter 直接升级成 uncaughtException，被运行期兜底一吞，run loop 就永远等不到 `done`：**任务卡死在 running、`stopTask` 返回 true 却停不掉、再发消息被 409 挡回，只有重启才能解**（复现方式见 `docs/incidents.md`）。用 `newListener` 钩子把错误压到有订阅者时再发。推论：以后凡是「同步造一个假 child 立刻报错」的写法，都要先问一句「消费者这时候订阅了吗」。
- **同一个数据库文件同一时刻只允许一个 server**，守卫在 `server/src/singleton.ts`（`index.ts` 先拿锁、再动态 import 会打开 DB 的模块）。**锁的粒度是 DB 文件路径，不是端口也不是仓库目录**——`PORT=x HARNESS_DB=/tmp/y.db` 起 throwaway 实例验证是既定工作流，必须继续允许并存。锁文件写 PID + 进程启动时间 + 端口 + token：判存活用 `process.kill(pid,0)`，再比对 `ps` 的进程启动时间**防 PID 复用误判**；释放时校验 pid+token 才 unlink，免得删掉别人的锁。逃生口 `HARNESS_ALLOW_MULTI=1`。理由：第二个实例**不占端口所以 `lsof` 查不出来**，但它的 `startScheduler` 照样 30s tick 同一个 DB、照样拉起 agent，而它起的子进程只在**它自己内存的 runs map** 里——UI 的停止请求打到另一个实例，`stopTask` 查不到就只改数据库不杀进程，于是「点了停止但进程还在跑」（实测发现的幽灵实例见 `docs/incidents.md`「端口撞车产幽灵」）。
- **启动期的致命错误必须 `exit(1)`，绝不能被运行期的兜底处理器吞掉**（`server/src/index.ts`）。两条硬规矩：①**`startScheduler()` 只在 listen 成功后的回调里调用**——一个连 HTTP 回调都收不到的进程，绝不许去轮询 schedules、拉起 agent；②顶部那两个 `unhandledRejection`/`uncaughtException` 兜底按 `startupComplete` 分流：启动期一律 `exitAfterStartupFailure`（关掉已绑定的 server、`singletonLock.release()`、exit 1），运行期才是原来那句「别让野生 SSE 异常搞垮 server」的只记录。释放锁走 `release()` 的 pid+token 校验，**不能误删同 DB 那个正常在跑的实例的锁**。理由：单实例守卫只挡「同一个 DB」，**端口撞车是另一条产幽灵的路**，而「不同 DB 并存」是既定的 throwaway 验证工作流，不能靠收紧锁粒度来解决（复现记录见 `docs/incidents.md`「端口撞车产幽灵」）。

## git、worktree 与验收

- **同一仓库的写型 git 操作全局串行,按仓库排一条队**（`withRepoLock`，`server/src/repo-lock.ts`；单测 `npm -w server run test:repo-lock`）。一个仓库的 `.git` 是所有 worktree 共用的**单一状态机**（ref、index.lock、`worktrees/` 注册表各只有一份），并行写不是「慢一点」而是互相拆台（三种拆台方式的实证见 `docs/incidents.md`「并行验收互相拆台」）。已纳入的写操作：`prepareWorktree` / `removeWorktree` / `mergeTaskBranch` / `cleanupAcceptedTask`，以及**整段** `acceptTask`。三条要点：①**排队等待,不是拒绝**——用户挨个点了 5 个任务的「验收通过」，这 5 个都该成功，只是一个接一个地合（同一任务的重复点击仍由 `acceptingTaskIds` 直接 409）；②锁**可重入**（持有者集合放在 `AsyncLocalStorage`），所以能同时锁在流程层与操作层，不必靠「调用方记得先加锁」的约定，也不会 `acceptTask → mergeTaskBranch` 自锁死；③整段验收持锁的意义是**守卫判断不会过期**——排在后面的验收拿到锁后才重新读任务与项目，看到的是前一个合并完成后的世界。排队要留痕：真等过就往时间线写一行「验收排队…已等待 Xs」，刷新后仍看得见，不是界面莫名卡几秒。边界：被唤醒去解冲突的 agent 在自己 worktree 里跑 `git merge`，那是独立进程，锁管不到（各 worktree 有自己的 index，只写自己的分支）。
- **「验收通过」是确定性后端动作**（POST `/tasks/:id/accept` / MCP `accept_task`），只在用户明确表示最终验收通过时触发，且永远不改 `TaskStatus`：running/queued 拒绝，其余停着的状态均可验收。独立 worktree 任务以 `harness/<id8>` 为源、`worktreeBase`（空则项目当前 symbolic branch）为目标，先判 ancestor，再试不动工作区的 `git fetch . <src>:<target>` fast-forward；非 FF 用临时 worktree `git merge --no-ff`，冲突只列文件并 abort，绝不强合，同时**把来源任务叫醒去解冲突**（`server/src/accept-conflict.ts`：不带 system 的 `continueTask`，让 followUpFrom 护住原终态；agent 在自己分支上合目标分支，解完再点验收就是 fast-forward）。目标恰在项目目录检出时，只有 `git status --porcelain` 为空才允许原地 merge；脏则报告不操作。确认已合并后先 prune，再删任务 worktree，最后只用 `git branch -d` 删分支（绝不用 `-D`，删不掉就停在 merged 如实报告）。三分类：普通任务保持原有验收语义；显式 `useWorktree=true` 的独立 worktree 执行者保留完整验收、合并与清理能力；`parentId` 指向 team 且 `useWorktree=false` 的共享执行者完全退出人工验收，单独 accept 一律 409（提示改为验收团队整体），团队级 accept 成功后统一合并/清理共享 worktree，并逐个把尚未 accepted 的共享执行者 stage 联动为 accepted。未启用 harness worktree 的普通任务/团队只标 accepted，因为不存在 harness 分支可清理。本规则是旧约定「不自动删 worktree/分支」的显式例外之一（另一个是删除任务时用户勾选「连 worktree 和分支一起删」，见下条）。
- **删除任务时提示「要不要连 worktree 和分支一起删」**（`server/src/workspace-cleanup.ts`：`detectTaskWorkspace` / `discardTaskWorkspace`）。任务行一删，`.worktrees/<taskId>` 目录和 `harness/<id8>` 分支在界面上就再没有入口了——不在删除那一刻问，用户就只能靠自己记得去 git 里收拾，攒几十个是迟早的事。四条要点：①**先问再删**：确认框打开时拉 `GET /tasks/:id/workspace`（目录 + 分支**各报各的**，被手删过目录、分支还在是常见状态），有残留才多出那个默认勾上的复选框，没有就是一句普通确认；②**删任务永远成功**：`DELETE /tasks/:id?worktree=1&branch=1[&force=1]` 先删任务行再清 git，git 那边失败不回滚删除，逐项结果（`worktreeRemoved`/`branchDeleted`/`worktreeError`/`branchError`）原样回给 UI；③**默认不带 force，让 git 自己的安全检查兜底**——脏 worktree 和未合并分支必须先被拒一次，把 git 原话摆给用户看，`--force` / `-D` 只在他看过报错又点了一次时才发出（这跟验收清理那条「绝不用 `-D`」不冲突：那是自动流程，这是用户明确要求删掉）；④**事后还能收拾**：`POST /projects/:id/workspaces/discard`（body 带 `taskId`）不查任务表、只按 taskId 推导路径与分支名，所以任务行早没了照样能删干净——第一次拒绝后的「强制删除」走的就是它。web 在 `DeleteTaskDialog`（`web-next/src/task-detail/DeleteTaskDialog.tsx`），mobile 在任务页 `confirmDelete` 的三选项 Alert。回归测试 `npm -w server run test:workspace-cleanup`。
- **worktree 没了要先想「能不能恢复」，恢复不了才重建，而且重建必须打断 agent 的记忆**（`prepareWorktree`，`server/src/git.ts`）。三档：目录还在 → 复用；目录没了但分支还在 → `git worktree add <path> <branch>` **恢复**（文件和提交原样回来，这是最该走的一档）；目录和分支都没了 → `-b` 建空壳并返回 `fresh:true`。目录被手删会留下陈旧注册（git 仍占着那个分支），所以建之前先 `git worktree prune`，把「我直接删了文件夹」拉回可恢复。`fresh` 必须一路传到调用方：**CLI 会话存在工作目录之外**（`~/.claude/projects/<转义 cwd>/`），`--resume` 接回来的 agent 记忆完好、文件却没了，不明说它就会接着「把最后一点补完」，产出建立在幻觉上——比直接报错更坏，因为要到 review 才发现。单任务走 `WORKSPACE_RESET`（同时写进时间线，刷新后可见）、团队调度台走 `LEAD_WORKSPACE_RESET`。回归测试 `npm -w server run test:worktree-recovery`。

## 团队与提问

- `/team` 团队模式：一个 `mode:"team"` 任务就是常驻调度台，状态只有忙（`running`）/闲（`idle`），**归档才是结束**；调度者不参与严格完成协议、不得调 `complete_task`，手头一轮说完只回到待命。执行者则是真实的普通任务：`tasks.parentId=<调度台 taskId>`，并落在 `groups.owner_task_id=<调度台 taskId>` 的内部组里，继续走严格完成协议、队列、单独重跑/换执行器/diff 等既有机制。执行者只在三种情况唤醒调度者：提问、失败、以及 `done && report_back=1`；普通完成静默，不再走 `scheduledMessages`。用户插话统一走 `POST /tasks/:id/reply`：在线时 `interrupt + send` 即时进入同一常驻会话，空闲回收后用同一个 `cliSessionId --resume` 接回，时间线实时与落盘一致。团队的 worktree 跟随全局 `worktreeDefault`（见下面「全局设置」一条），创建团队时也可显式指定；开启后调度台与默认执行者共享同一个 worktree，某个执行者再显式 `useWorktree:true` 才在共享分支之上另开隔离。理由：整队必须看见同一份文件，同时执行者仍保留可调度、可追踪、可恢复及按需隔离的真任务语义。
- `team_presets` 是全局的团队创建快捷方式，只保存可配置的 `TeamConfig` 组合并在新建团队时一次性填入；套用后 task/team 与预设**没有持续绑定**，后续微调、重命名或删除预设都不回写已创建团队。预设里的执行器 id 悬空时，读取展示与套用都按对应 lead/worker 类型降级到当前默认执行器。
- **凡是对 `tasks.status` 做校验的地方，都要先问一句「这条对常驻调度台适用吗」**。一次性任务的状态机是「跑→终态」，`status !== "running"` 约等于「没在干活」；常驻调度台的 status 只在 `beginTurn`/`endTurn`（`server/src/team/session.ts`）之间来回切，重启后接回时更是 `idle`，**它明明活着却会被这类挡板拦住**。已知需要 team 例外的：`/ask`（调度者向用户提问）、`/answer`、`/reply`、`/run`（idle 不是终态，点运行 = 接回同一 CLI 会话）；明确不适用的：`/complete`、`/pause`（调度者不走严格完成协议，也没有检查点语义）。**改一处就 grep 一遍所有 status 校验点**——同一个文件里两个对称端点只改了一个，这类漏点靠通读发现不了（事故见 `docs/incidents.md`「对称端点只改了一个」）。
- `ask_question` 的候选答案（`tasks.question_options`，json `string[]`）是**建议答案不是单选题**：网页把每条渲染成按钮，**点一下是把该选项原文填进输入框、不发送**——已有手写内容时换行追加，确认后再点「发送答复」才走 `POST /tasks/:id/answer`。这一步是刻意的：这类答复往往是不可逆决策（选「先做 A」会立刻派出一批执行者），点错一次代价不小；填入而非直发也才对得上「输入框始终留着供自由作答（答别的、答组合都行）」。答复链路、resume 语义、团队转发全部零改动。选项只写「一句能直接当答复读的话」，理由和取舍留在 `question` 里。上限常量（`MAX_QUESTION_OPTIONS` / `MAX_QUESTION_OPTION_LEN` / `MAX_QUESTION_ITEMS`）单点在 `shared`，server 校验、MCP 工具描述、网页渲染共用；超限一律 400 **不静默截断**（悄悄砍掉一个候选，agent 以为它还在、用户压根没见过）。提问态的出现/消失走独立 SSE 事件 `task.question`（`task.status` 只带状态字段，不捎 question），否则答完卡片还杵在那像是没答上。理由：选项是给答复者省打字的快捷方式，不该在协议层多开一条「选项答复」的路。
- **一次问多个问题走 `tasks.question_items`**（json `{question, options?}[]`，上限 4 题）：顶层 `question` 退化成**共同背景/引言**，顶层 `options` 只服务旧式单问题——两者同传一律 400（否则引言会被当成一道可回答的题）。答复仍是**一条文本**走同一个 `/answer`：按 `【i】问题 / 答：…` 编号对应，**未答的必须显式写「(未答)」，不许静默省略**——agent 得能区分「用户跳过了」和「用户没看见」，省略会让它以为那题不存在、然后自己脑补一个答案。不做 `multiSelect`、不做选项的 `description`/`header`：前者已被「填入输入框 + 换行追加」天然覆盖，再加一套是机制打架；后者会鼓励把说明塞进选项，跟上一条拧着来。执行者提问转发给调度者时（`server/src/team/inbox.ts`）要把多问题连同候选完整展开，脏 JSON 解析失败退回纯问题、不拖垮通知。

## 执行器与模型

- **哪些 CLI 能派任务,单一真相来源是 `server/src/executors/catalog/`**(一个 CLI 一个 spec 文件:检测字段 + 非交互命令行构造 + parser + resume 方案 + 可选的自定义 factory)。增删一个智能体只有两步:shared 的 `AGENT_TYPES` 加/删一个字符串 + 目录加/删一个 spec 文件;两边漏一边**编译不过**(`catalog/index.ts` 的 `SPECS` 挂着 `satisfies Record<AgentType, CliSpec>`)。`build()`(`executors/index.ts`)只按 `spec.factory` 分派:claude/codex 走专用类(常驻会话、诊断链路),其余全部 `GenericCliExecutor`。**别再往 `build()` 里加 switch 分支,也别在第三个地方抄一张 CLI 名单**(detect.ts、MCP 工具 schema、会话恢复命令都已改成派生)。字段含义、自定义 parser 写法、`untested` 标注约定见 `catalog/README.md`。三条不许破的:①`GenericCliExecutor` 一律不实现 `openResident`——「谁能当团队调度者」的过滤就靠它存在与否;②预检失败仍走 `failedChild` 的惰性 emit(见上面「进程与启动」那条),parser 必须保证事件流一定以 `done` 收尾;③密钥只走 `spec.exec.relay` 的 `env`,绝不进 argv。回归测试 `npm -w server run test:cli-catalog`。

- **所有 AI 调用统一走本地 CLI 执行器**，不存在第二条「直连 HTTP」的路。派任务、续跑与辩论都经 `resolveExecutor(type)` / `resolveExecutorById(id)` 起一个真 CLI 进程。供应商（`llm_providers`）**只是执行器的一个属性**（`agents.provider_id`）：挂上就在起 CLI 前注入 base_url + key（claude 走 `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` 环境变量；codex 走 `-c model_providers.harness_relay.*` 且 `env_key` 指向环境变量名），于是 `claude@官方` 和 `claude@公司自建` 是两个并列的执行器，都能执行任务。`server/src/llm.ts` 只剩 `listModels`（配供应商时拉模型列表）。理由：两套 AI 调用体系（CLI vs 直连）意味着两套配置 UI、两种能力上限（直连没工具、干不了活），合并成一条后「选谁干活」在任何场景下都是同一个下拉。
  - 推论一：**key 绝不进命令行**。`commandLine` 会存进 `sessions.command_line` 并在 UI 展示，所以 codex 用 `env_key` 而非 `bearer_token`，真 key 只走进程 env；另有 `redactSecrets()`（`server/src/executors/spawn.ts`）兜底脱敏。展示用的恢复命令带 env 前缀但 token 是占位符，存在 `sessions.relay_env`（`toSession` 恒重算 resumeCommand，不能指望 executor 当初写进 DB 的那份）。
  - 推论二：`llm_providers.base_url` 存**根地址**（不含 `/v1`），但读取侧一律过 `relayRoot()` / `relayApi()`（`server/src/llm.ts`）归一，不要自己拼字符串——历史数据和手滑都可能已经带了 `/v1`，硬拼会打到 `/v1/v1`。`ANTHROPIC_BASE_URL` 用 `relayRoot`（SDK 自己补 `/v1`），codex 的 `model_providers.*.base_url` 与 `listModels` 探测用 `relayApi`（已是 `/v2` 之类就原样保留）。
  - 推论三：挂了供应商的执行器，「模型」下拉列的是**该供应商 `/v1/models` 拉到的全名**（`claude-opus-4-5-…`），不是 CLI 别名（`opus`）——供应商认的是自己那套 id，别名多半不存在。所以 UI 上「供应商」chip 排在「模型」前面：先定上游，才知道有哪些模型可选。
- 任务执行器从 type 升级为 profile：`tasks.executor_id` / `TeamConfig.leadExecutorId` / `TeamConfig.workerExecutorId` 指向 `agents.id`，解析统一走 `resolveExecutorFor({ executorId, type })`（`server/src/executors/index.ts`）。规则是 **executorId 非空且查得到就用具体 profile；为空或已删除则按 agentType/team lead/worker 的 type 取当前默认执行器降级**。`agentType` 仍保留，用于展示、筛选和降级；删除执行器时把直接引用它的 `tasks.executor_id` 置空，team JSON 里的旧 id 也必须靠 `resolveExecutorFor` 平滑降级。任务返回给前端时带只读 `executorLabel`，team 对象里带 `leadExecutorLabel` / `workerExecutorLabel`，都来自当前 `agents.name`。新增任何“选谁干活”的表面都必须同时使用前端 `ExecutorPicker`、持久化 `executorId` 字段和后端 `resolveExecutorFor`；自查时 grep 写死的 agent 类型列表，辩论链路曾因此漏过一次。
- 任务级 `model` / `reasoningEffort` 非空时覆盖执行器 profile，null 时继续跟随 profile；覆盖解析的单点是 `resolveExecutorFor`，所有为任务启动 CLI 的 fresh/resume/辩论/团队路径都只把任务或 TeamConfig 上的值传进这里，不在各 executor 或调用点另造优先级。`speed` 仍只属于执行器 profile，不做任务级覆盖。
- **任务级 `model` / `reasoningEffort` 覆盖是「针对某个特定执行器」的覆盖，绝不能脱离执行器单独流动**。判定与取值的单点是 shared 的 `sameExecutor` / `inheritExecutorOverrides`（`shared/src/executor-overrides.ts`，走 `@harness/shared/executors` 子路径导出），配套的「这个任务用哪个执行器」判定是同文件的 `pickExecutor`；单测 `npm -w server run test:executor-overrides`。三条规矩：
  - **创建路径**：只有任务最终解析到的执行器与默认值所属的执行器**一致**时才继承默认的 model/effort；任务显式换了 `agentType` 或 `executorId` 导致解析结果不同 → 两者落 null（跟随新执行器自己的 profile）。显式传的值永远生效。一致性粒度是**解析后的 executorId 相同**（都为 null 时才退回比 agentType）——同类型换 profile 可能换了供应商，模型 id 各认各的（见上文供应商推论三）。已接入：team `dispatch`（`server/src/team/dispatch.ts`）、`POST /groups/:id/tasks/batch`（`batch_create_tasks` / `create_task_chain` 共用）。
  - **编辑路径**（`PATCH /tasks/:id`）：本次 PATCH 让执行器解析结果相对 existing 变了、且没有显式给 model/effort → 自动把两者清成 null。
  - **前端**：换执行器时模型/思考强度选择器一律重置为「跟随执行器」，清空动作放在**组件层**而不是各调用点——web 在 `web-next/src/composer/executorOverrides.ts`、`ReplyBox` 与 `TeamPresetEditor` 的编辑入口统一处理，mobile 在 `ExecutionConfig`（三处调用点共用）。判定同样调 `sameExecutor`，不要自己写 `next.agentType !== cur.agentType`。
  - 顺带的口径统一：批量建任务里「任务自己的 `agentType` 撞上**继承来的** `defaults.executorId`」不再 400，而是按「这个任务换类型」降级（与 dispatch 一致）；只有**同一处显式给出的** executorId + agentType 冲突才报 400。理由见 `docs/incidents.md`「claude CLI 拿到 GPT 模型名」——执行器解析早就有「换类型不硬套默认 profile」的逻辑，只有 model/effort 没跟着走同一条。
  - 实现约束：`shared/src/index.ts` **不能**转发 `executor-overrides` 里的运行时函数。服务端直接跑 shared 的 `.ts` 源码，而 Node 的类型擦除不会把 `"./x.js"` 说明符映射回 `"./x.ts"`——index 里现有的 `./session.js` 全是 `import type`（编译期就被抹掉）才没出事，一加真正的运行时转发进程立刻起不来。要共享运行时函数就照 `@harness/shared/team` 那样开子路径导出。

## 数据与设置

- **schema 里删掉字段或整表时，同一轮把老库对象也退役掉**：列登记进 `RETIRED_COLUMNS`，表登记进 `RETIRED_TABLES`（`server/src/db/index.ts`）；`ensureSchema()` 末尾分别按 `PRAGMA table_info` / `sqlite_master` 判存在再 drop（幂等；失败只 warn 不拦启动），同时删掉对应的建表和 `ALTER ... ADD COLUMN`（否则每次启动一加一删打架）。登记前提：全仓 grep 确认没有任何读写，且数据已无恢复价值。理由：留着不删的代价不是那点空间，是**每次 `db:push` 都要拿「about to delete X with N items / THIS ACTION WILL CAUSE DATA LOSS」吓唬人一次**，真正该看的 schema 变更淹没在里面，久了就养成无脑 abort 的习惯。
- **全局设置统一存进 `app_settings` 通用 KV 表**，读取时把持久化值覆盖到 shared 的 `DEFAULT_APP_SETTINGS` 上；`worktreeDefault` 出厂为 `true`。普通任务、团队调度台、辩论衍生任务以及 `batch_create_tasks` / `create_task_chain` 在调用方未传 `useWorktree` 时都跟随该默认，显式 true/false 优先，但项目不是 git repo 时一律落 false。团队 dispatch 出来的 worker 是例外：它的 `useWorktree ?? false` 表示“是否在团队共享目录之上再开一层隔离”，刻意不跟随全局默认。
- Codex 单任务每一轮必须保留失败证据链：`data/runs/<taskId>/` 下按 session+turn 写原始 `codex exec --json` 事件、stderr 和结构化 diagnostics；`turn.failed`、signal、静默非零退出等诊断同时写进会话 Markdown，保证实时页面与刷新后都能看到。诊断写入是 best-effort，不得反过来改变 agent 原本的退出结果。
